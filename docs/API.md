# API Guide

> Purpose: API discovery and contract ownership. Last updated: 2026-11-16. Owner: backend engineering.

## Contract rules

- Versioned governed endpoints use `/api/v1`.
- Authentication is necessary but resource ownership/tenant authorization is checked separately.
- Mutation and durable-job creation endpoints use idempotency keys where duplicate side effects or provider charges are possible.
- Long-running operations return durable job/run references; clients recover through reads and SSE/status updates.
- Proposal writes validate canonical paths/values and use version checks against MongoDB authority.
- Public proposal payloads use an allowlisted projection.

## Version-aware vendor submissions

- `GET /api/vendor-responses/workspace?proposalId=...` requires a scoped `vendor:submit` public grant. It validates the grant against the proposal, lazily publishes the deterministic questionnaire when needed, and returns only the allowlisted vendor workspace contract: access state, questionnaire, draft, and current submission. Raw grant tokens, owner/organization IDs, private upload URLs, and unrelated proposal fields are never returned. Initial workspace reads may use a recipientless proposal grant; recipient-bound actions remain subject to their stricter checks.
- `POST /api/vendor-responses/questionnaires/publish` requires authentication, `vendor-response:write`, and proposal ownership. The body is `{ "proposalId": "..." }`. Publishing unchanged source data is idempotent; a changed proposal projection creates questionnaire version `n + 1` and supersedes the previous published version.
- `POST /api/vendor-responses/drafts` creates or resumes the one active draft for the validated invitation. The JSON body is `{ "proposalId": "..." }`. A new draft returns `201`; a resume returns `200`. The response includes the contract-shaped partial response and an allowlisted `documentManifest`, never grant material, private URLs, or object keys.
- `GET /api/vendor-responses/drafts/:draftId?proposalId=...` resumes an active, unexpired draft within the same tenant, proposal, grant ID, and grant-subject hash.
- `PATCH /api/vendor-responses/drafts/:draftId` saves a partial contract-shaped response. The body is `{ "proposalId": "...", "draftRevision": 3, "response": { ... } }`. Documents are server-managed and cannot be added through this JSON endpoint. A stale revision returns `409` with code `draft_conflict` and `latestDraftRevision`; it never overwrites the newer draft.
- `POST /api/vendor-responses/drafts/:draftId/documents?proposalId=...` accepts multipart field `documents` plus `draftRevision`, `purposeId`, `scopeType`, and optional `scopeId`. Supply the grant in the `x-rfpilot-access-grant` header or query because authorization runs before multipart bytes are accepted. Files must satisfy the pinned questionnaire category, scope, extension, detected MIME type, size, per-category count, global count, and malware-scan rules before association.
- `DELETE /api/vendor-responses/drafts/:draftId/documents/:documentId?proposalId=...&draftRevision=...` retires one active draft document and removes its structured references. Its private object is deleted only when no immutable submitted version references the document.
- `DELETE /api/vendor-responses/drafts/:draftId?proposalId=...&draftRevision=...` abandons a draft. A daily cleanup retires expired/abandoned draft objects, retaining any object referenced by an immutable submitted version and retrying provider failures.
- `POST /api/vendor-responses/drafts/:draftId/finalize` accepts `{ "proposalId": "...", "draftRevision": 3, "submissionIdempotencyKey": "..." }`; the key may instead be sent as `Idempotency-Key`. The server checks the current proposal lifecycle, validates the complete response against its pinned questionnaire, verifies the exact active document manifest, stamps accepted acknowledgements, calculates the authoritative totals, and creates one immutable structured version. A replay returns `200` with the original safe receipt; a new version returns `201`. The receipt includes the questionnaire reference, calculation snapshot, document disposition, and checksum but excludes private URLs, object keys, and the full response payload.
- `POST /api/vendor-responses/:submissionId/revision-drafts` accepts `{ "proposalId": "..." }` and creates or resumes a draft from that submission's current structured version. The submission must belong to the same tenant, proposal, and public grant. Documents from the current version are marked inherited; retiring one records its source version without deleting submitted evidence, while new uploads are marked added.
- `GET /api/vendor-responses/check` returns the stable submission ID, current version number, latest version ID, revision eligibility, and the latest compatibility response.
- `POST /api/vendor-responses` accepts `submissionIdempotencyKey` (or `Idempotency-Key`) and optional `submissionReason`. It creates version 1 or a new immutable revision; an idempotent replay returns the original version and receipt.
- `GET /api/vendor-responses/receipt/:versionId?proposalId=...&email=...` requires the same scoped `vendor:submit` public grant and a normalized vendor-email match. It returns version, checksum, timestamps, and safe file metadata without private object URLs.
- `POST /api/vendor-responses/manual` records a response the vendor delivered outside the portal. It requires authentication, `vendor-response:write`, and ownership of the proposal, and writes the same submission/version chain with `sourceSystem: "planner_upload"`. Neither the planner notification nor the vendor confirmation email is sent.
- `GET /api/vendor-responses/proposals` returns the planner's paginated proposal groups with counts and the exact owned response IDs in each displayed group so the dashboard can build an explicit, page-scoped deletion selection.
- `DELETE /api/vendor-responses/:id` permanently deletes one owned vendor response, its Mongo submission/version chain, and its private document objects. It requires authentication and `vendor-response:write`; a response outside the planner's tenant/ownership scope is returned as not found.
- `DELETE /api/vendor-responses` accepts JSON `{ "responseIds": ["..."] }` and permanently deletes that explicit selection (1–100 unique response IDs). Every requested response must belong to the authenticated planner in the active tenant; if any response is unavailable, the operation fails closed without deleting the rest. Registered document sources are tombstoned while immutable governed analysis and audit outputs follow their existing retention windows.

## Requirement registry

All routes are available by default without feature-flag environment variables. They still require an authenticated organization membership and proposal ownership. Reads require `proposal:read`; mutations require `proposal:write` and `Idempotency-Key`. Edit/approve requests also require the current set lock version through `If-Match` (or `expectedVersion`).

- `POST /api/v1/proposals/:proposalId/intelligence/requirement-sets` creates or idempotently returns a deterministic draft from current proposal fields and accepted rendered-RFP narrative.
- `GET /api/v1/proposals/:proposalId/intelligence/requirement-sets` lists versions with requirement counts and freshness.
- `GET /api/v1/proposals/:proposalId/intelligence/requirement-sets/:setId` returns the set, evaluation matrix, criteria, requirements, exact source locators, validation, and freshness reasons.
- `PATCH /api/v1/proposals/:proposalId/intelligence/requirement-sets/:setId/requirements/:requirementId` edits bounded review fields with optimistic locking.
- `POST .../:setId/approve` validates confirmed weights and completed human review, then freezes the version.
- `POST .../:setId/supersede` links an approved set to a new draft generated from the current proposal.

- Existing authenticated list/detail endpoints return current version metadata while retaining their response shape.

## Organization Accounts: how the sections fit

The sections from here to "Launch metrics" document the Organization Accounts API (ORG-101 … ORG-607), each endpoint once, in this order:

| Area | Sections |
|---|---|
| Sign-in and organization setup | Sign-in (Google, Microsoft, company SSO) · Organization SSO connection · Two-factor authentication · Organization domains · Domain-match access requests · Organization profile (with onboarding) |
| People | Organization members · Teams · Organization invitations · RFP sharing |
| Working with RFPs | Dashboard RFP queries · RFP lifecycle · Support access grants · Organization audit log |
| Plans and shared resources | Plans and entitlements (with plan management for RFPilot staff) · Organization vendor list · RFP templates |
| RFPilot staff only | Legacy customer placement · Launch metrics · Organization account detail · Staff access to an organization's content (plus the staff halves of support access and plan management) |

Conventions that hold across these sections:

- **Roles.** Customer roles are Owner (`owner`), Admin (`organization_admin`), Team Manager (`team_manager`), Planner (`planner`) and Viewer (`viewer`). What each may do is one table, `src/modules/identity/domain/authorizationPolicy.ts`; which RFPs each may reach is `src/modules/identity/domain/rfpAccessPolicy.ts`. RFPilot staff are not members of customer organizations: the staff routes for support access, plan management and launch metrics need a staff role **and** an account in the `admins` collection.
- **Refusals.** On member routes, another organization's resource answers 404, the same as a missing one, and a resource in the caller's organization that they may not reach answers 403. A role refused by the route guard gets 403 `{ success: false, message }` with no `code`; refusals decided later carry a `code`.
- **Wording.** The fixed text the API returns for display (refusal and error `message`s, audit labels, the workflow headline, form-contract labels and helper texts, the assistant's fixed answers) says "proposal" ("This member still owns 3 proposals. Reassign them first.", "Proposal not found."), not "RFP" (rule changed 2026-11-12; `tests/proposal-wording-guard.test.js`). Codes, routes and field names keep `rfp` (`OWNER_HAS_RFPS`, `ownedRfpCount`, `/rfps`), so a client must branch on `code`, not on the message text. Three things can still say "RFP": text a model writes (assistant replies, vendor analysis; the prompts and knowledge text are not converted), requirement titles derived from field keys ("RFP Timeline Notes"), and stored codes shown as stored, such as `scope: rfp` and `operation: rfp.read` in the audit CSV's Details column. The prose in this document still says RFP for the same document.
- **Tenant.** On member routes the organization comes from the session, never from the request. The public invitation and access-request routes take it from the invitation or the matched email domain, and the staff routes (support access, plan management, the organization account detail and staff access to an organization's content) name a customer organization in the path.
- **Plans.** A plan limits two things only: how many RFPs an organization may create, and the `vendorResponses` and `proposalIntelligence` features (see "Plans and entitlements"). Every other Organization Accounts route is open on every plan.

## Sign-in: Google, Microsoft and company SSO

Customers sign up with email and password (confirmed by an emailed 6-digit code), or sign in with Google, Microsoft or their organization's own OpenID Connect provider. Setting `PASSWORD_SIGN_IN_ENABLED=false` turns the password, signup-OTP and reset routes (and password invitation accept) off; they then answer 410 `PASSWORD_SIGN_IN_DISABLED`. Setup for operators and customer IT: [SSO_SETUP.md](SSO_SETUP.md).

`POST /api/auth/sso/discover` `{ email }` (dashboard server only: BFF key required, else 403) answers `{ method: "company" | "password" }` for the sign-in page's email-first step: `company` when an active SSO connection covers the email's domain. It never names the organization. Limited to 30 per 15 minutes per visitor; the dashboard passes the visitor's IP in `x-rfpilot-client-ip`, which is trusted only alongside a valid BFF key. A bad email is 400 `VALIDATION_ERROR`. Rules in `src/modules/sso/`.

- `GET /api/auth/sso/start?kind=microsoft|company&email=&invite=&bind=`: `bind` is the lowercase hex SHA-256 of the dashboard's `rfp_sso_bind` cookie; `email` is required for `company`. Redirects (302) to the IdP, or to `${FRONTEND_URL}/sign-in?error=CODE` (`/invite/<token>?error=CODE` when `invite` was given).
- `GET /api/auth/sso/callback`: the redirect URI registered with every IdP. Success redirects to `${FRONTEND_URL}/sso/complete?handoff=…` (single use, 60 s).
- `POST /api/auth/sso/exchange` `{ handoff, bind }` (BFF key required): answers like `POST /api/auth/google`, including the 2FA step. Company SSO never gets our 2FA prompt; Microsoft follows `TWO_FACTOR_SSO_POLICY` like Google.
- Account rules: a first company sign-in joins the connection's organization as Planner (a pending invitation's role wins when signing in from the invite); a first Microsoft sign-in creates a new organization with the person as Owner. A company IdP may only sign in emails on the connection's domains that its organization still has verified. Microsoft work-tenant emails are trusted only with `xms_edov=true`.
- Error codes in the redirect: `SSO_INVALID_REQUEST`, `SSO_NOT_CONFIGURED`, `MICROSOFT_NOT_CONFIGURED`, `SSO_PROVIDER_UNAVAILABLE`, `SSO_STATE_INVALID`, `SSO_CANCELLED`, `SSO_IDENTITY_INVALID`, `EMAIL_MISSING`, `MICROSOFT_EMAIL_UNVERIFIED`, `COMPANY_EMAIL_UNVERIFIED`, `SSO_DOMAIN_NOT_ALLOWED`, `SSO_IDENTITY_MISMATCH`, `SSO_REQUIRED`, `EMAIL_IN_ANOTHER_ORGANIZATION`, `MEMBER_DEACTIVATED`, `USER_BLOCKED`, `SSO_INVITE_ORG_MISMATCH`, plus invitation refusal codes. Exchange errors: 401 `SSO_HANDOFF_INVALID`.
- Require SSO: when an organization requires it, emails on its connection's domains are refused on Google and Microsoft sign-in and invite accept (403 `SSO_REQUIRED`), except the organization's Owner (break-glass) and people whose account belongs to another organization.
- `POST /api/v1/invitations/lookup` includes `invitation.companySso` (true when the inviting organization has an active connection for the invited email's domain).

## Organization SSO connection

Routes under `/api/organization/sso` (`organization:manage`). One OIDC connection per organization; the client secret is sealed with `SSO_SECRET_KEY` and never returned.

- `GET /api/organization/sso` → `{ connection | null, requireSso, redirectUri, verifiedDomains }`; `connection` is `{ issuer, clientId, hasClientSecret, domains, status: "draft"|"active", lastTestedAt, lastTestOutcome, version, updatedAt }`.
- `PUT /api/organization/sso` `{ issuer, clientId, clientSecret?, domains, version? }` (secret required on create; `version` for updates) → `{ connection }`. Refusals: 400 `VALIDATION_ERROR`, 422 `SSO_DOMAIN_NOT_VERIFIED` with `domains` (unverified, or used by another organization's connection), 422 `SSO_ISSUER_UNREACHABLE`, 409 `VERSION_CONFLICT`.
- `POST /api/organization/sso/test` → `{ ok, issuer, authorizationEndpoint, problems[] }` (discovery and signing keys; no sign-in).
- `PUT /api/organization/sso/status` `{ status }` → `{ connection }`. Turning it off (draft) also turns Require SSO off.
- `PUT /api/organization/sso/require` `{ requireSso }` → `{ requireSso, signedOutMembers }`; 409 `SSO_CONNECTION_NOT_ACTIVE`. Turning it on signs out the non-Owner members on the connection's domains (not the person making the change).
- `DELETE /api/organization/sso` → `{ success }`; also turns Require SSO off. 404 `SSO_CONNECTION_NOT_FOUND` where there is none.

## Two-factor authentication (ORG-303, ORG-304)

Routes in `routes/twoFactorRoute.ts` (`/api/auth/2fa`) and `routes/organizationSecurityRoute.ts`; rules in `src/modules/twoFactor/`.

- `POST /api/auth/2fa/disable` `{ password?, code | recoveryCode }`: a current TOTP or recovery code is always required. `password` is required too unless the account is linked to Google sign-in, which may have no password its owner knows; a wrong password is never ignored (401 `REAUTHENTICATION_FAILED`).
- Wrong codes are counted per account across challenges and IPs, and each attempt is counted before the code is checked. Ten failures lock the second factor for 15 minutes (429 `TWO_FACTOR_LOCKED` with `Retry-After`); each further lock before a successful code doubles, up to 24 hours. Signed-in 2FA endpoints are also limited per user, whatever the IP.
- `POST /api/organization/members/:userId/two-factor/reset` answers 409 `TWO_FACTOR_RESET_SHARED_ACCOUNT` when the member is also active in another organization: the enrolment belongs to the person, so only DXG support resets it.

## Organization domains (ORG-305)

Routes under `/api/organization/domains` (`organization:manage`); rules in `src/modules/domainVerification/`.

- `POST /api/organization/domains` `{ domain }` answers 201 with the TXT record to publish, also for a domain another organization already holds verified: the response never says a domain is taken. Such a domain stays `pending` and its checks report `lastCheckOutcome: "not_verified"`, because only one organization can hold a domain verified. Refusals: 400 `DOMAIN_INVALID`, 422 `DOMAIN_NOT_VERIFIABLE` (public mail providers), 409 `DOMAIN_LIMIT_REACHED`, 409 `DOMAIN_ALREADY_ADDED`.
- The cron worker checks due domains every 15 minutes, five at a time, leasing each record so concurrent tasks don't check it twice. A check that errors is retried after an hour (`dns_error:<code>` or `check_failed`).

## Domain-match access requests (ORG-306)

Someone signing up with an email on a company domain already in use is offered "Request access" instead of silently getting a separate organization. A domain matches the organization that **verified** it (ORG-305); failing that, the oldest active organization with an active member whose own email (proven by code or SSO when the account was made) is on that domain. Claimed-but-unverified domains with no such member, public mail providers and reserved example domains never match, and a match never reveals more than the organization's name, which only someone who passed the emailed code sees. Rules in `src/modules/accessRequests/`.

- `POST /api/auth/verify-otp` (signup) also answers `organizationMatch: { name } | null`.
- `POST /api/auth/register`, `POST /api/auth/google`: a NEW account on a matched domain answers 409 `ORGANIZATION_DOMAIN_MATCH` with `organizationName`, unless the body has `separateOrganization: true` (the person chose to create their own organization). Existing accounts sign in as before. A first Microsoft or company-SSO sign-in that would create an organization on a matched domain redirects with `error=ORGANIZATION_DOMAIN_MATCH`; the person can request access through email signup.
- `POST /api/auth/access-requests` `{ email, name }` (public; 5 per 15 minutes per email and IP). The email must hold a verified signup code (403 `EMAIL_NOT_VERIFIED`), which the request uses up. Answers 201 `{ status: "pending" | "invited", organizationName }`; `invited` when the organization auto-approves its domain (the invitation is sent at once, in the Owner's name); auto-approve applies only to a DNS-verified match, never to a member-email match. 409 `NO_ORGANIZATION_MATCH`, 409 `ACCOUNT_EXISTS`, 400 `INVALID_NAME`. Repeating a pending request is a no-op. Owners and Admins get a bell notification (`type: "access_request"`) and an email.
- Routes under `/api/v1/organization/access-requests` (`organization:manage`, own organization only):
  - `GET ?status=pending|approved|denied|all` (default `pending`) → `{ data: [{ id, email, name, status, autoApproved, decidedAt, createdAt }] }`.
  - `POST /:id/approve` `{ role?, teamId? }` (default Planner) sends an ordinary invitation; no account exists until it is accepted. Invitation refusals pass through with their codes.
  - `POST /:id/deny` emails the requester, who can still create their own organization.
  - Deciding twice: 409 `ACCESS_REQUEST_NOT_PENDING`; another organization's request: 404 `ACCESS_REQUEST_NOT_FOUND`.
  - `GET|PUT /settings` `{ autoApproveDomain }` → `{ autoApproveDomain, verifiedDomains }`; audited as `organization.settings.updated`. Turning it on with no verified domain is 409 `NO_VERIFIED_DOMAIN`.
- Audit actions: `organization.access_request.created`, `.auto_approved`, `.approved`, `.denied`.

## Organization profile

Routes under `/api/organization/profile`; rules in `src/modules/organizationProfile/`.

- `GET /api/organization/profile` (any member) answers `{ name, type, industry, country, timeZone, eventsPerYear, plan, onboardingStep, canManage }`.
- Onboarding (ORG-301): every organization created at sign-up (password, Google, Microsoft or company SSO) starts at `onboardingStep: "details"` and walks `details → plan → team → done`; organizations from before onboarding are `"done"`. The dashboard sends an Owner or Admin (`canManage`) to the onboarding wizard until the step is `"done"`.
- `PUT /api/organization/profile` `{ name, type?, industry?, country?, timeZone?, eventsPerYear? }` (`organization:manage`) saves the details and moves `"details"` on to `"plan"`. The name is trimmed with inner whitespace collapsed, 1–200 characters; `type` is one of `corporate|association|agency|venue|government|other`; `industry` up to 120 characters; `country` an ISO 3166-1 alpha-2 code; `timeZone` an IANA zone; `eventsPerYear` a whole number 0–100,000. A field left out is unchanged; `""` or `null` clears it. Otherwise 400 `VALIDATION_ERROR` with `field`. Audited as `organization.settings.updated` (`organization_onboarding_details` or `organization_details_updated`).
- `POST /api/organization/onboarding/plan` `{ plan: "free_trial" }` (`organization:manage`) records the plan and moves on to `"team"`; allowed at the plan or team step, otherwise 409 `ONBOARDING_STEP_CONFLICT` with the current `onboardingStep`.
- `POST /api/organization/onboarding/complete` (`organization:manage`) finishes onboarding from the team step (inviting is optional); repeating it once done is a no-op; earlier steps answer 409 `ONBOARDING_STEP_CONFLICT`.
- Every profile and onboarding write answers the whole profile, as GET does, and is rate-limited (30 per 15 minutes).

## Organization members

Membership management (ORG-206, ORG-207, ORG-307) lives in `routes/organizationMembersRoute.ts`, mounted at `/api/organization`, Owner/Admin only; rules in `src/modules/organizationMembers/application/manageMembers.ts`. Every write takes the member's current `version` (409 `STALE_VERSION` otherwise).

- `PATCH /members/:userId/role` `{ role, version }`. Becoming a Viewer while owning RFPs is 409 `OWNER_HAS_RFPS` with `ownedRfpCount`, checked again in the same transaction as the write. A demotion by someone else revokes all the member's sessions at once; any other role change revokes the member's other sessions on their next request (see DECISIONS.md).
- `PUT /members/:userId/teams` `{ teamIds, version }` makes the member's active teams exactly `teamIds` (ORG-201 Teams), keeping manager flags on teams they stay on and leaving archived teams' memberships as history. An archived team or another organization's team is 400 `UNKNOWN_TEAMS` with `unknownTeamIds`.
- `DELETE /api/users/:id` (legacy, platform admins only; no dashboard screen calls it) hard-deletes an account. It is refused with 409 `OWNER_HAS_RFPS` and `ownedRfpCount` while the user owns any RFP in any organization, so RFPs are never orphaned; organization members are deactivated and their RFPs reassigned instead.

## Teams

Team administration (ORG-201) lives in `routes/teamsRoute.ts`; rules in `src/modules/teams/application/manageTeams.ts`. Every change writes a `SecurityAuditEvent` (`team.created`, `team.renamed`, `team.archived`, `team.member_added`, `team.member_removed`, `team.manager_changed`).

- `GET /api/v1/teams` — Owners and Admins get every team with its members; other members get `{ id, name }` for active teams.
- `POST /api/v1/teams` `{ name }`, `GET|PATCH /api/v1/teams/:teamId` `{ name }`, `POST /api/v1/teams/:teamId/archive` — Owner/Admin only. Active names are unique per organization, ignoring case (409 `TEAM_NAME_TAKEN`). Archived teams can't be changed (409 `TEAM_ARCHIVED`).
- `POST /api/v1/teams/:teamId/members` `{ userId, isManager? }`, `PATCH /api/v1/teams/:teamId/members/:userId` `{ isManager }`, `DELETE /api/v1/teams/:teamId/members/:userId` — Owner/Admin only. Members must be active in the organization; a manager must hold the `team_manager` role (422 `TEAM_MANAGER_ROLE_REQUIRED`).
- Proposal team (ORG-202): `POST /api/proposals` and copy put a new proposal on its creator's team when they're on exactly one active team (a client-sent `teamId` is ignored). `PUT /api/proposals/:id` with `teamId` (an active team in the organization, or `null`) changes it for anyone allowed to edit; anything else is 422 `TEAM_NOT_ASSIGNABLE`. Resending the current team's id is accepted even after that team is archived.
- Proposal writable fields: `POST /api/proposals` and `PUT /api/proposals/:id` take the RFP content sections (`event`, `venueSchedule`, `roomByRoom`, `production`, `hybridVirtual`, `contentCreative`, `venue`, `uploads`, `budget`, `contact`, `proposalSettings`; `PUT` also accepts dotted paths below them such as `event.eventName`) and the flags `status`, `isDraft`, `isActive`, `isFavorite`, `isAccepted`, `isOpen` and `teamId` (edit only, see above). Every other key is ignored without an error: `_id`, `userId`, `createdAt`, `updatedAt`, `isArchived`, `archivedAt`, `isCopy`, `viewsCount`, `version`, `lifecycle`, unknown fields, dotted paths into any of them and `$`-prefixed keys at any depth. Archive, restore, award and view counts have their own routes. A payload whose `organizationId` is not the caller's organization is refused: 400 `{ success: false, code: "PROPOSAL_TENANCY_FIELD_NOT_WRITABLE", message }`, nothing is written. Prototype keys (`__proto__`, `constructor`, `prototype`) are dropped like `$` keys, and content nested more than 64 levels deep is refused: 400 `PROPOSAL_PAYLOAD_TOO_DEEP`.

## Organization invitations (ORG-203)

Routes in `routes/invitationRoute.ts`, rules in `src/modules/invitations/domain/invitationRules.ts`.

- `GET /api/v1/organization/invitations?status=` lists invitations the caller may manage (Owner/Admin: all; Team Manager: their teams, when `allowManagerInvites` is on).
- `POST /api/v1/organization/invitations` `{ email, role, teamId? }` invites one person; `POST .../bulk` `{ emails: string | string[], role, teamId? }` takes up to 500 entries and answers with one result per row (`invited`, or `refused` with a code such as `INVALID_EMAIL`, `DUPLICATE_IN_LIST`, `ALREADY_INVITED`, `ALREADY_MEMBER`, `EMAIL_IN_ANOTHER_ORGANIZATION`, `LEGACY_ACCOUNT_PENDING_PLACEMENT`). `teamId` must be an active team of the organization (else `404 TEAM_NOT_FOUND`); on accept the member is added to it in the same transaction, or joins without a team if it was archived in between. An email whose invitation is past its expiry can be invited again at once, before the sweep marks it expired.
- `POST .../:id/resend` rotates the link (the old one stops working at once) and restarts the 7-day expiry; `POST .../:id/revoke` withdraws it.
- Sending limits (create, bulk and resend): the shared limiter allows 30 requests per 15 minutes per inviting user and 60 per organization (`429`, `Retry-After`). Each organization may queue at most `INVITATION_DAILY_EMAIL_LIMIT` invitation emails per UTC day (default 500), counting one per recipient, so a bulk paste counts every row that would be invited; a request that would go over is refused whole with `429 INVITATION_DAILY_LIMIT`, `remaining` and `Retry-After` (seconds to the next UTC day). An invitation can be resent once every five minutes (counted from the invite or the last resend): `429 INVITATION_RESEND_COOLDOWN` with `retryAfterSeconds`. Day-six reminders and delivery retries aren't counted.
- Public, token in the body: `POST /api/v1/invitations/lookup` `{ token }` returns organization, role, inviter, email and whether an account exists. `POST /api/v1/invitations/accept` `{ token, email, password }` signs an existing account in (the email must equal the invited one); `POST /api/v1/invitations/accept/register` `{ token, name, password }` creates the account in the inviting organization. `POST /api/v1/invitations/accept/google` `{ token, idToken }` is for accounts with no usable password (created by Google sign-in) and for Google sign-up: the verified Google email must equal the invited one (`403 INVITATION_EMAIL_MISMATCH`; a bad ID token is `401 INVALID_GOOGLE_IDENTITY`); an existing account joins, otherwise an account is created in the inviting organization with no organization of its own. All three return a session like `/api/auth/login`; the Google accept, like `/api/auth/google`, may instead return the 2FA step (`twoFactorRequired`). Role, team and organization come only from the invitation.
- Emails (ORG-204) go through `utils/emailService.ts` (`sendTransactionalEmail`, no fixed-recipient copy) and link to `${FRONTEND_URL}/invite/<token>`, so `FRONTEND_URL` must be the dashboard origin. The cron worker's invitation sweep (every 15 minutes) expires invitations, sends the day-six reminder once per link with a fresh link, and retries failed sends up to five attempts. Under `NODE_ENV=test` mail goes to an in-memory recorder.
- Dead links answer `404 INVITATION_INVALID` or `410` with `INVITATION_EXPIRED`, `INVITATION_REVOKED`, `INVITATION_ALREADY_USED` or `INVITATION_SUPERSEDED`; none of them names the organization or email.

## RFP sharing

Sharing (ORG-208) lives in `routes/rfpSharesRoute.ts`; rules in `src/modules/rfpSharing/application/manageRfpShares.ts`. Who may share is the access policy's `share` decision: the proposal's owner, a manager of its (active) team, or an Owner/Admin.

- `GET /api/v1/proposals/:proposalId/shares` lists shares as `{ userId, permission, grantedBy, memberActive, createdAt, updatedAt }`. `memberActive: false` marks a deactivated member's share, which is kept but grants nothing.

The member must be active in the same organization (404 `MEMBER_NOT_FOUND`, 409 `MEMBER_INACTIVE`); Viewers get view only (422 `VIEWER_VIEW_ONLY`). Grants and revocations write `proposal.share_granted` / `proposal.share_revoked` audit events.

## Dashboard RFP queries (ORG-401)

`routes/rfpDashboardRoute.ts`, rules in `src/modules/rfpDashboard/`. Both endpoints need `proposal:read` and return only what `rfpListScope` lets the member see: everything in the organization for Owners and Admins, their managed teams' RFPs for Team Managers, their own for Planners, plus anything shared with them. Filters only narrow that set. Saved copies are never listed.

- Filters (both endpoints): `stage` (comma-separated lifecycle stages; default is every stage except `archived`), `owner` (user id), `team` (team id), `eventFrom` / `eventTo` (inclusive, `YYYY-MM-DD`, against the event start date; RFPs without a start date drop out), `venueCity` (whole name, case-insensitive), `search` (event name contains). An invalid value is 400 `DASHBOARD_FILTER_INVALID`, never silently ignored.
- `GET /api/v1/rfps` — adds `page`, `limit` (max 100, default 25), `sortBy` (`updatedAt` default, `createdAt`, `eventStartDate`, `eventName`) and `sortOrder`. Items: `{ id, eventName, stage, status, isDraft, ownerUserId, ownerName, teamId, teamName, eventStartDate, eventEndDate, venueCity, vendorsInvited, vendorsResponded, reviewStartedAt, awardedAt, createdAt, updatedAt, permissions }` with `pagination { total, page, limit, totalPages }`.
- Row permissions: every item of `GET /api/v1/rfps`, and every item of the Proposals page's list `GET /api/proposals` (all its tabs, including `archived=true` and `isCopy=true`), carries `permissions: { canEdit, canDuplicate, canArchive }` for the signed-in member. Each flag is the answer the mutation endpoint would give, from the same two checks it runs (`src/modules/identity/domain/rfpRowPermissions.ts`): the route's `proposal:write` capability and the access policy action its query is scoped by.
  - `canEdit`: `PUT /api/proposals/:id` (and `PATCH /api/proposals/:id/meta`, scoped the same way), policy action `edit`. True for an Owner or Admin and, among members whose role can write proposals (Team Manager, Planner), for the proposal's owner, a manager of its active team, and a member with an edit share. Never true for a Viewer, even as the proposal's owner or with an edit share.
  - `canDuplicate`: `POST /api/proposals/:id/copy`, policy action `view` (the source is only read; the copy belongs to the caller). True for anyone with `proposal:write` who can see the row, so a view-only share may save a copy and a Viewer may not. It does not say whether the plan has a slot left (403 `PLAN_LIMIT_REACHED`, see "Plans and entitlements").
  - `canArchive`: `DELETE /api/proposals/:id` and `PATCH /api/proposals/:id/restore`, policy action `archive`. Never true through a share. On an archived row it means the member may restore it.
  - The flags report permission, not state: the client still decides what an archived row or a saved copy offers. There is no `canDelete`; who may permanently delete is an open product decision, and `DELETE /api/proposals/:id/permanent` keeps answering for itself. Previewing needs no flag (a listed row can always be opened).
  - They are computed from each row's own owner and team and the actor the request already resolved, so they add no query. `GET /api/proposals` reads `organizationId`, `userId` and `teamId` for this and does not return them.
- `GET /api/v1/rfps/summary` — over exactly the list's set: `{ total, activeRfps (sent + receiving_responses + under_review), responsesReceived (sum of vendorsResponded), awardedThisQuarter, byStage, quarter { label, start, end, timeZone } }`. "This quarter" is the calendar quarter in the organization's `timeZone` (UTC when unset). The integration suite checks, over randomized filters, that the summary equals aggregating every list page.
- An RFP the lifecycle backfill hasn't reached yet is listed with the stage its flags give (archived, draft, otherwise sent).
- Measured on 5,000 RFPs in one organization (integration suite, local Docker): p95 16–136 ms against the 300 ms budget.

## RFP lifecycle (ORG-403)

Every RFP has a derived stage, stored on the proposal as `lifecycle` and recomputed after each write: `draft` → `sent` → `receiving_responses` → `under_review` → `awarded`, or `archived`. Archived outranks everything, an unpublished proposal is a draft, then awarded, then under review (a vendor comparison was opened), then receiving responses (at least one vendor response), else sent. Rules in `src/modules/proposalLifecycle/`. Clients can't write `lifecycle`: create, update and copy strip it.

- `POST /api/proposals/:id/award` — "Mark as awarded". Needs `proposal:publish` and edit access to the RFP (403 / 404 otherwise). Only a sent, unarchived RFP qualifies (409 `PROPOSAL_NOT_AWARDABLE`). Returns `{ stage, awardedAt, awardSource, awardedByUserId, changedAt }`. Repeating it keeps the first award time. A planner's award replaces one set by a comparison, and a comparison never overrides a planner's.
- `DELETE /api/proposals/:id/award` — withdraws the award, whichever source set it. Same permissions and response.
- `GET /api/proposals/:id/status-history` — `proposal:read` and view access. Returns the same fields plus `transitions`, oldest first: `{ fromStage, toStage, fromStatus, toStatus, actorType: user|vendor|system, actorUserId, reason, at }`, capped at 500.
- Recording a comparison decision (`POST /api/v1/proposals/:proposalId/intelligence/comparisons/:runId/decisions`) also moves the stage: `selection` awards the RFP (source `comparison`), and a later `shortlist` or `no_award` withdraws that award. Creating a comparison starts the review.

## Support access grants (ORG-404)

Routes in `routes/supportAccessRoute.ts`; rules in `src/modules/supportAccess/`.

**Changed on 2026-11-17 (owner's decision, `DECISIONS.md`): a grant no longer gates anything.** RFPilot staff read every organization's content with no grant (see "Staff access to an organization's content"). The organization side below still answers, unchanged, because the dashboard released before the decision may still call it; it is to be removed, with its model and data, in a later change. Creating or revoking a grant still writes `support_access.granted` / `.revoked` in the organization, but those events are no longer shown in the customer audit log, and a grant's `activity` and `events` stay empty from now on because staff reads are no longer recorded in the customer organization.

Organization side (Owner and Admin only; other roles get the route guard's plain 403, and a staff account 403 `SUPPORT_GRANT_FORBIDDEN`):

- `POST /api/v1/organization/support-grants` `{ proposalId?, expiresInDays? | expiresAt?, reason? }` creates a grant for one RFP (`proposalId`) or, without it, the whole organization. Expiry defaults to 7 days and is refused past 30 (400 `INVALID_GRANT_EXPIRY`). An RFP outside the organization is 404 `PROPOSAL_NOT_FOUND`.
- `GET /api/v1/organization/support-grants?page=` lists active and past grants, newest first: `{ id, scope: "organization" | "rfp", rfp, reason, status: "active" | "expired" | "revoked", grantedBy, createdAt, expiresAt, revokedAt, revokedBy, activity: { useCount, lastUsedAt } }`.
- `GET /api/v1/organization/support-grants/:grantId` adds `events`. Since the decision of 2026-11-17 staff activity is not shown to customers: `events` is always `[]` and `activity` is always `{ useCount: 0, lastUsedAt: null }` on every grant answer, including for `support_access.used` rows stored before the decision (kept in the database, never read by these endpoints). The fields stay so the response shape is unchanged.
- `POST /api/v1/organization/support-grants/:grantId/revoke` ends a grant at once (409 `SUPPORT_GRANT_EXPIRED` if it already expired; revoking twice is a no-op). Another organization's grant is 404 `SUPPORT_GRANT_NOT_FOUND`.

RFPilot staff side, the older routes the deployed admin app calls (a staff membership role and an `admins` account with an admin role; customers get the route guard's plain 403, and a `users` account holding a staff role 403 `SUPPORT_ACCESS_FORBIDDEN`). They now read **without a grant**, through the same service, guard, rate limit and staff-side audit as the new routes, and keep their answer shapes so the deployed admin app keeps working. The admin app is rebuilt against the new routes in a later PR.

- `GET /api/v1/admin/support-access/organizations/:organizationId/rfps?page=&search=` → `{ organizationId, grants, rfps, pagination }`: every proposal of the organization (20 per page, newest update first; `search` matches the event name).
- `GET /api/v1/admin/support-access/organizations/:organizationId/rfps/:proposalId` → `{ organizationId, grant, rfp, owner }`. `…/vendor-responses` → `{ organizationId, grant, proposalId, vendorResponses }`.
- `GET /api/v1/admin/support/tickets/:ticketId/rfps?page=&search=` → `{ organizationId, grants, rfps, pagination }`: the requester's proposals in the ticket's organization. The ticket is looked up in whichever organization it belongs to; an unknown ticket is 404 `SUPPORT_TICKET_NOT_FOUND`. A ticket with no requester on record answers an empty list; it never lists the organization's other proposals.
- `grant` / `grants`: these used to be the grant the read was made under. They are now one **standing entry** for the organization: `{ id: <the organization's id>, scope: "organization", proposalId: null, expiresAt, secondsRemaining }`, where `expiresAt` is always 30 days from the moment of the request. Nothing expires; the field is there because the deployed admin app's banner and its check that "the grant is still active" need it.
- `GET /api/v1/admin/support-access/grants` ("granted to me") keeps its shape, `{ grants: [{ id, scope, proposalId, expiresAt, secondsRemaining, organization: { id, name }, rfp, reason, createdAt }] }`, and now returns **one standing entry per organization** (every organization, customer organizations first, then by name; at most 2,000), whatever grants exist: `scope: "organization"`, `rfp: null`, `reason: null`, `createdAt` the organization's creation date. This is deliberate: the deployed admin app opens an organization from this list, and every 30 seconds closes a screen whose organization is missing from it. It carries organization names only, so it writes no audit event. It lists every organization, so it shares the staff content rate limit (`organization-content-read`, 300 per 15 minutes per staff account): the admin app's poll is 30 requests per 15 minutes per open screen. Over the limit it answers 429 like the content routes. Past 2,000 organizations the ones cut off are still readable by id on the new routes.
- Errors: 400 `INVALID_ORGANIZATION_ID` / `INVALID_PROPOSAL_ID` for a malformed id; 404 `ORGANIZATION_NOT_FOUND` for an unknown organization; 404 `PROPOSAL_NOT_FOUND` for a proposal that isn't in the organization named in the path (the same answer as an id that doesn't exist). `SUPPORT_GRANT_REQUIRED` is no longer returned.
- Audit: one `platform.organization_content.read` event per read in the **staff** organization (see below). `support_access.used` and `support_access.denied` are no longer written by anything; rows written before 2026-11-17 stay in the database.
- `GET /api/admin/proposals` and `GET /api/admin/proposals/:id` were removed on 2026-11-17 (DECISIONS) and answer the API's 404 like any unknown path.

## Helpdesk (support tickets)

Routes in `routes/supportDeskRoute.ts`; rules in `src/modules/supportDesk/`. Customers write to RFPilot support from the dashboard and RFPilot staff answer from the admin app. Decision: `DECISIONS.md`, 2026-11-12.

Customer side (`/api/v1/support/...`, any active member): create, list, open, reply, resolve, unread count, attachments. A member sees only the tickets they opened, in their own organization; any other ticket, including a colleague's and another organization's, is 404 `SUPPORT_TICKET_NOT_FOUND`. Internal notes and triage activity never leave through these routes, and the customer hears from "RFPilot support", never a named agent.

Agent side (`/api/v1/admin/support/...`, route guard: a staff membership role; the service then decides the scope in `agentScopeFor`):

- **RFPilot staff** (an `admins` account holding a staff role, the ORG-404 / ORG-603 test) work **every organization's tickets**: `GET /tickets` (inbox), `GET /metrics` (stat cards, unread and overdue), `GET /tickets/:ticketId`, `POST /tickets/:ticketId/messages`, `POST /tickets/:ticketId/notes`, `PATCH /tickets/:ticketId` (assignee, status, priority, category, subject), `POST|DELETE /tickets/:ticketId/presence`, `GET /tickets/:ticketId/attachments/:attachmentId`, `GET /agents` (every unblocked staff account) and the canned replies.
- A `users` account holding a staff membership role is refused: 403 `SUPPORT_FORBIDDEN`. A `users` account whose account role is administrative is an agent of its own organization only, as before: another organization's ticket is 404 for it. (Its tickets are now owned by RFPilot staff, whose names it does not resolve and whom it cannot pick as assignee.)
- What staff read here is the ticket conversation and its attachments. The requester's proposals are read at `GET /api/v1/admin/support/tickets/:ticketId/rfps`, with no grant since 2026-11-17 (see "Support access grants" and "Staff access to an organization's content").
- `GET /tickets?status=&assignee=&priority=&category=&search=&organization=&sort=&page=&perPage=` returns `{ scope, tickets, pagination }`. `scope` is `all_organizations` for RFPilot staff and `organization` otherwise. Each ticket carries `organization: { id, name }` (the customer organization it belongs to), `requester` and `assignee`. `organization=<id>` narrows the staff inbox to one organization (400 `SUPPORT_INVALID_ID` for a malformed id; ignored outside staff scope). `search` matches the subject, the requester's name or email, a ticket number when the whole search is one (`#3` or `3`) and, for staff, the organization's name. Name matches are capped (the 200 newest matching accounts and 50 newest matching organizations in staff scope), so a very common term can miss tickets; narrow by organization.
- `GET /tickets/:ticketId` returns `{ ticket, organization, requester, assignee, messages }`.
- **Ticket numbers are per organization** and are the numbers customers see; they are not unique across organizations. A number search returns every match, each with its organization; number plus `organization` is exact. Agent alerts name the organization beside the number.
- Replies, notes and status events are written into the ticket's organization. Canned replies and an agent's pending uploads stay in the agent's own organization.
- New tickets are assigned to the RFPilot staff account with the fewest active tickets across all organizations. Bell notifications (and the admin app's real-time alert, which rides on them) go to the ticket's owner, or to every staff account when it has none, when it is escalated or when the customer marks it resolved; the alert email goes to `SUPPORT_DESK_NOTIFY_EMAIL`.
- Reading or answering a ticket writes no `SecurityAuditEvent` in the customer's organization.

## Organization audit log (ORG-407)

`routes/auditLogRoute.ts`, rules in `src/modules/auditLog/`. Read-only view of the caller's own organization's `SecurityAuditEvent` rows (PRD P0-10). Owner and Admin only (`audit:read` in `authorizationPolicy.ts`); every other role gets the route guard's plain 403. The organization always comes from the session, never from the request. Open on every plan.

- `GET /api/v1/organization/audit-events?actor=&action=&category=&from=&to=&limit=&cursor=` returns `{ events, nextCursor }`, newest first. `actor` is a member's user id. (`actor=support`, which used to select RFPilot Support activity, is still accepted and returns nothing.) `action` is one catalogued action, `category` one of the keys below. `from` is inclusive and `to` exclusive (ISO timestamps with `Z` or an offset; anything else is refused); a bare `YYYY-MM-DD` is read as UTC, and a bare `to` date includes that whole day. `limit` defaults to 50 and is capped at 100. A bad filter is 400 `AUDIT_FILTER_INVALID`.
- An event is `{ id, occurredAt, action, label, category, decision, reason, actor, target: { type, id, name }, details }`. `actor` is `{ kind: "member", id, name, email }`, `{ kind: "unknown", id, name: "Unknown user" }` for an id that isn't a member of the organization, or `{ kind: "system" }`. `target.name` is filled only when the target is a member. `target.id` is null for a session (`refresh_session`): the id means nothing to a reader. `details` is an allowlist of scalar metadata (`role`, `previousRole`, `setting`, `from`, `to`, `scope`, `operation`, `domain`, `grantId`, ...); anything else a writer stored, and any value containing an email address, is left out. `reason` is shown only when it is a machine code.
- `GET /api/v1/organization/audit-events/filters` returns `{ categories: [{ key, label, actions: [{ value, label }] }] }` for the filter controls. Since 2026-11-17 there is no `support_access` category, no staff action and no `supportActor` option.
- `GET /api/v1/organization/audit-events/export` takes the same filters (no paging) and returns `text/csv`, newest first, up to 5,000 rows; `X-Audit-Export-Truncated: true` means the date range should be narrowed. Action and category labels say "Proposal" ("Proposal shared", "Proposal sharing"); target types, detail keys and values, role and result codes are exported as stored (`proposal`, `proposalId`). Stored codes are not reworded. Until 2026-11-16 the file reworded those two names to `rfp` and `rfpId`. Cells that a spreadsheet would run as a formula (leading `=`, `+`, `-`, `@`, tab or carriage return) are prefixed with an apostrophe. Limited to 20 exports per user per 15 minutes.
- The view is an allowlist (`AUDIT_CATALOG` in `src/modules/auditLog/domain.ts`): sign-in (`auth.session.created`, `auth.login.failed`, session revocations), two-factor, invitations and access requests, members and roles, teams, proposal sharing (`sharing`, labelled "Proposal sharing"), organization settings (profile, domains, SSO) and the vendor list. An action that isn't catalogued (for example `auth.refresh.rotated`) is never returned. Not catalogued, by decision (2026-11-16, `DECISIONS.md`): the template actions (`proposal_template.*`, ORG-604). Customers do not see them; the events are still written for staff and forensics. **A new audited action must be added to the catalog to appear.**
- **Staff activity is not shown to customers (owner's decision, 2026-11-17).** `AUDIT_CATALOG` is the customer-visible catalog and holds no staff-attributed action and nothing about support access. `STAFF_ONLY_ACTIONS` names the seven actions that are stored in customer organizations and never returned: `support_access.granted`, `support_access.revoked`, `support_access.used`, `support_access.denied`, `organization.legacy_customer.placed`, `organization.legacy_customer.placement_rolled_back` and `organization.plan_changed`. Any action named `support_access.*`, `platform.*` or `admin.*` is refused as well. The list, the filter options and the CSV export cannot return one: asking by `action` or by `category=support_access` is 400 `AUDIT_FILTER_INVALID`, and `actor=support` or a staff member's id returns nothing. Stored rows are not deleted. An action whose actor is an `admins` account must not be added to the catalog without a new decision.
- `auth.login.failed` (new in ORG-407) is written when a password sign-in fails on a known account (`reason`: `wrong_password` or `account_blocked`), in that account's organization. It carries the user id, never the email or password. An unknown email has no organization and writes nothing.
- `DELETE /api/auth/sessions/:id` now writes `auth.session.revoked` only when a session was actually revoked. Before ORG-407 it recorded the id from the request even when it matched nothing (the isolation sweep caught another organization's session id echoed into the caller's audit log).

## Plans and entitlements (ORG-601)

Rules in `src/modules/entitlements/`. Pricing is by RFPs created; the plan table (`domain/plans.ts`) is the only definition of a plan's limit and features. The server enforces it; the dashboard only reads it.

- Plans: `free_trial` (2 RFPs created per organization, vendor responses and RFP intelligence locked) and `full_access` (no limit, both features; assigned by DXG staff until paid plans exist). `PLAN_FREE_TRIAL_PROPOSAL_LIMIT` overrides the free-trial limit. An absent or unknown plan value is treated as `free_trial`. Legacy holding tenants are exempt.
- `GET /api/organization/entitlements` (any member) answers `{ data: { plan, exempt, proposals: { created, limit, remaining, canCreate }, features: { vendorResponses, proposalIntelligence } } }` for the caller's organization; `limit` and `remaining` are `null` when there is no limit.
- Creating an RFP (`POST /api/proposals`, `POST /api/proposals/:id/copy`) takes one slot in the same MongoDB transaction that inserts it. `Organization.proposalsCreated` counts every RFP created through the API since ORG-601 and never goes down, so archiving or deleting one doesn't free a slot. With no slot left the answer is 403 `{ success: false, code: "PLAN_LIMIT_REACHED", message, plan, limit, created }`.
- Locked features answer 403 `{ success: false, code: "PLAN_FEATURE_LOCKED", message, title, status, plan, feature }` before the handler runs, whatever ids the request carries:
  - `vendorResponses`: `GET /api/vendor-responses`, `/proposals`, `/:id`, `/:id/submission-detail`, `/:id/submission-export` and `PATCH /:id/read`.
  - `proposalIntelligence`: every route under `/api/v1/proposals/:proposalId/intelligence/` (requirement sets, evidence extraction, vendor intelligence, evaluation, comparisons, clarifications, reports, retention and legal holds). No request can queue an intelligence job for a locked organization.
  - Both: `/api/v1/vendor-responses/:responseId/analysis-*` (jobs, runs, export).
- Open on every plan: the vendor submission routes (workspace, drafts, finalize, receipt, revisions), questionnaire publish and rollout, recording a response on a vendor's behalf, deleting a response by id, and public-access grants. Submissions received while locked are stored and readable once the plan changes. The planner's notification for a response received while locked says only that a vendor responded (`metadata: { planLocked: true, feature: "vendorResponses" }`).
- Not plan features, so open on every plan: teams, members, invitations, sharing, the dashboard queries, the RFP lifecycle routes, support access grants, the audit log, the vendor list and templates. Starting an RFP from a template takes an RFP slot like any other create (403 `PLAN_LIMIT_REACHED`).
- `tests/plan-entitlements.test.js` lists every route of the RFP intelligence, vendor analysis, vendor response, audit log and template routers with the feature it requires; a new route in one of those routers fails that test until it is classified. Other routers, the staff-only ones included, are not covered by that test.

### Plan management for RFPilot staff (ORG-603)

Mounted at `/api/v1/admin/organization-plans`. RFPilot staff only: the caller needs a staff membership role (`dxg_admin` or `super_admin`) **and** an `admins` account with role `admin` or `super_admin`. Every customer role gets 403, and a `users` account holding a staff role gets 403 `PLAN_MANAGEMENT_FORBIDDEN`. These are the only routes that can set `full_access`.

- `GET /` `?search=&page=` lists customer organizations by name, 20 per page (`search` matches name, slug or an organization id). Answers `{ data: { organizations: [{ id, name, slug, status, createdAt, plan, proposals: { created, limit, remaining, canCreate }, features }], plans: [{ id, proposalLimit, features }], pagination, filters } }`. `plans` is the plan table, so the admin app doesn't hard-code limits. Legacy holding tenants are exempt from plans and aren't listed.
- `GET /:organizationId` answers `{ data: { organization, plans, history } }`; `history` is the last 20 plan changes, newest first: `{ at, fromPlan, toPlan, note, changedBy: { id, name } | null }`.
- `PUT /:organizationId` `{ plan: "free_trial" | "full_access", note?: string (≤ 500) }` sets the plan and answers the same shape as GET plus `changed`. Raising and lowering are both allowed and apply on the customer's next request. Setting the plan the organization already has answers `changed: false` and writes nothing. Rate-limited to 120 writes per 15 minutes per staff account.
- Each change writes one `organization.plan_changed` audit event in the organization whose plan changed, in the same MongoDB transaction as the plan: actor (the staff account), `metadata.fromPlan`, `metadata.toPlan`, `metadata.proposalsCreated`, `metadata.actorOrganizationId` and the optional `metadata.note`.
- Errors: 400 `INVALID_PLAN` or `INVALID_PLAN_NOTE`; 404 `ORGANIZATION_NOT_FOUND` for a missing organization, a malformed id or a legacy holding tenant (identical bodies); 409 `PLAN_CHANGE_CONFLICT` when someone else changed the plan between the read and the write.
- A downgrade keeps the organization's RFPs, stored vendor responses and `proposalsCreated`; it locks the features and refuses new RFPs once the count is at the limit. AI jobs queued before a downgrade still finish (DECISIONS, ORG-603).

### Organization account detail for RFPilot staff

`GET /api/v1/admin/organizations/:organizationId` (`routes/adminOrganizationPlansRoute.ts`, `src/modules/entitlements/application/organizationAccountDetail.ts`). Read-only. It returns account-level information about any organization: the response is an allowlist of counts, settings and timestamps. (The decision that staff see "nothing else" without a grant was superseded later on 2026-11-17: the member list and customer content are read from the routes under "Staff access to an organization's content".) This route itself is unchanged; it never carries a member list (no names, emails, roles or ids of members other than the Owner), and never customer content (proposal titles or bodies, vendor companies or contacts, template titles, ticket subjects or messages, invitation emails, team names, plan-change notes, and a support grant's scope, expiry, reason or proposal; invitations, the vendor list and templates are not read at all, not even counted) or secrets (SSO issuer, client id or secret, domain verification tokens, hashes). Those still need a grant ("Support access grants").

- Who: the same guard as plan management, a staff membership role **and** an `admins` account with role `admin` or `super_admin`. Every customer role gets the route guard's plain 403; a `users` account holding a staff role gets 403 `PLAN_MANAGEMENT_FORBIDDEN`; no session 401. Rate-limited to 300 reads per 15 minutes per staff account.
- Unlike the plan routes it also answers for a legacy holding tenant and for RFPilot's own organization, and says which it is (`organization.standing`).
- Errors: 400 `INVALID_ORGANIZATION_ID` for an id that is not 24 hex characters; 404 `ORGANIZATION_NOT_FOUND` for an unknown organization.
- Audit: each successful read writes one `platform.organization_account.read` event in the **staff** organization's audit trail (actor: the staff account; `targetType: "organization"`, `targetId`: the organization read; `metadata.agentAccountType: "admin"`) before anything is returned, and the read fails if the event can't be written. Nothing is written in the customer's organization, and the action is not in the customer audit catalog, so the customer's audit log never shows it. A refused, invalid or not-found request writes no event.
- Cost: at most 13 MongoDB reads and 1 write per request, each read keyed on the organization id (10 run in parallel). Proposals are counted from the `organizationId` index with `countDocuments`; no proposal document is loaded, which is why there is no archived count and no last-update time (no existing index covers them). Teams are one `$group`, members one `$group` over that organization's membership rows.

`data` is `{ organization, owner, plan, counts, security, activity, supportAccess }`:

### Staff access to an organization's content

`routes/adminOrganizationContentRoute.ts`, `controller/adminOrganizationContentController.ts`, rules in `src/modules/staffAccess/` (service `application/readOrganizationContent.ts`, Mongo reader `infrastructure/mongoStaffOrganizationReader.ts`). Owner's decision, 2026-11-17 (`DECISIONS.md`): RFPilot staff can **view** everything in every organization with no grant and no action from the organization. **Read-only: every route in that file is a GET.** Staff do not edit or delete proposals, templates or vendor data. Staff member management is a separate set of routes: see "Staff member management" below.

- Who: `authenticate`, a staff membership role (`dxg_admin` or `super_admin`), **and** an `admins` account with role `admin`, `super_admin` or `superadmin` (`isPlanStaff`, the check plan management uses). Every customer role gets the route guard's plain 403; a `users` account holding a staff role gets 403 `STAFF_ACCESS_FORBIDDEN`; no session 401.
- Rate limit: 300 reads per 15 minutes per staff account (`organization-content-read`), shared with the older support-access routes, including the "granted to me" organization list.
- The organization is the one in the path. It is validated (400 `INVALID_ORGANIZATION_ID` unless 24 lower-case hex characters), looked up (404 `ORGANIZATION_NOT_FOUND`), and named in every query; the session's organization and anything in the query string or body are ignored. Any organization can be read, including a legacy holding tenant and RFPilot's own. A proposal or template that belongs to another organization than the one in the path is 404 (`PROPOSAL_NOT_FOUND`, `TEMPLATE_NOT_FOUND`), the same answer as an id that doesn't exist; a malformed record id is 400 (`INVALID_PROPOSAL_ID`, `INVALID_TEMPLATE_ID`); a filter value outside its list is 400 `INVALID_FILTER`.
- Every answer is `{ success: true, data }` and `data.organizationId` is the organization read. Each view is an allowlist built field by field; no stored document is passed through.
- **Never returned, by any route:** password hashes, two-factor secrets or recovery codes, federated identities (`googleId`, SSO subjects), session or refresh tokens, invitation tokens and token hashes, public access tokens or grants (the vendor links), SSO client ids and secrets, domain verification tokens, a proposal's `proposalSettings`, `candidateApplicationIds` and `__v`, vendor response documents (only their count), and any AI or provider payload. None of these is selected from MongoDB in the first place.
- Storage: all of it is MongoDB. No Postgres table is read, so there is no tenant (RLS) context to set; if a later staff read needs Postgres it must run under the target organization's tenant context, as the member-facing reads do.
- **Audit (staff side only).** Each successful read writes exactly one `platform.organization_content.read` event in the **staff** organization's audit trail: actor (the staff account), `targetType: "organization"`, `targetId` (the organization read), `reason` and `metadata.resource` (below), `metadata.recordId` when one record was opened, `metadata.ticketId` for the ticket route, `metadata.agentAccountType: "admin"`. It is awaited before data is returned, and the read fails (500) if it cannot be written. A request that ends in **404** (organization, proposal, template or ticket not found, including a record that belongs to another organization) writes one `platform.organization_content.denied` event, also in the **staff** organization: `decision: "denied"`, `reason` the error code in lower case (`organization_not_found`, `proposal_not_found`, `template_not_found`, `support_ticket_not_found`), `targetId` and `metadata.organizationId` the organization the path asked for (absent for a missing ticket), `metadata.resource`, and `metadata.recordId` or `metadata.ticketId`. The 404 is returned even if that event cannot be written; the failure is logged. A 400 (malformed id or filter), 401, 403 or 429 writes nothing. **Nothing is written to the customer organization**, and the action is not in the customer audit catalog, so customers cannot see that staff read their content.

The only staff writes on a customer organization are the plan (`PUT /api/v1/admin/organization-plans/:organizationId`), legacy-customer placement, and blocking and reactivating the whole organization ("Staff organization block", below). `tests/staff-organization-routes-guard.test.js` walks every router `server.ts` mounts and fails if any route under `/admin/organizations/:organizationId` other than `POST /block` and `POST /reactivate` is not a GET.

`routes/adminOrganizationMembersRoute.ts`, `routes/adminOrganizationTeamsRoute.ts`, their controllers, services `src/modules/staffAccess/application/manageOrganizationMembers.ts` and `manageOrganizationTeams.ts` (each has one method, the read), reads `infrastructure/mongoStaffMemberDirectory.ts` and `mongoStaffTeamDirectory.ts`. #### Rows that staff member and team management left behind

Staff changed members and teams between 2026-11-18 and 2026-11-24. What they wrote is kept, and what reads it is kept, so existing rows behave exactly as they did.

- **Staff audit rows.** The staff organization's audit trail keeps its `platform.organization_member.role_changed`, `.deactivated`, `.reactivated`, `.proposals_reassigned`, `.ownership_transferred`, `.teams_changed` and `platform.organization_team.created`, `.renamed`, `.archived`, `.member_added`, `.member_removed`, `.manager_changed` rows. `STAFF_MEMBER_AUDIT` and `STAFF_TEAM_AUDIT` (`src/modules/staffAccess/domain.ts`) still name every one of them, as the catalog for those rows; only `.read` is written now. - **Teams staff created** have no `createdBy`. Nothing reads it for a decision.
- **Session markers.** A staff change that ended sessions left three markers so that nothing about it would later appear in the customer's audit log: revoke reason `staff_membership_changed` on a refresh session, `sessionRevocationStaff` on a membership (with the pending-revocation flag), and `suspendedByStaff` on a membership staff deactivated. **No route sets any of them any more.** Their readers stay (`src/modules/auth/composition.ts`, `application/staffCausedSessionRevocation.ts`, `application/manageSessions.ts`):

    | Customer-side event | When the customer flow writes it | For a row that carries a staff marker |
    |---|---|---|
    | `auth.refresh.reuse_detected` ("Session reuse detected") | a revoked session presents its refresh token | Not written when the session's revoke reason is `staff_membership_changed` (or `staff_organization_blocked`) and the token presented is that session's own last one. The refresh is refused the same way (401 `REFRESH_SESSION_EXPIRED`, `reason: "reuse_detected"`). An older, already-rotated token, a session revoked for any other reason, and every replay on a live session are detected and recorded as before. |
    | `auth.sessions.revoked_others` (`membership_role_changed`) | the member's next request after a role change that is not a demotion | Not written when the pending flag carries `sessionRevocationStaff`. The member's other sessions are revoked the same way (for the staff reason), the requesting one is kept, and the flag and its marker are cleared. |
    | `auth.sessions.revoked_all` (`membership_inactive`) | a deactivated member makes a request, or refreshes, while a session is still live | Not written when the suspended membership carries `suspendedByStaff`. Every session is revoked the same way (for the staff reason) and the request is 401 `MEMBERSHIP_INACTIVE`. |

    The two revocations are recorded in the **staff** organization as `platform.organization_member.sessions_revoked` (`decision: "revoked"`, `reason` `membership_role_changed` or `membership_inactive`, `actorUserId` the staff account whose change caused it, `targetId` the member, `metadata`: `organizationId`, `memberUserId`, `revokedCount`, `keptSession`, `trigger: "member_request"`), only when at least one session was revoked, best effort. With no marker every path is the customer flow, unchanged. The accepted limits of 2026-11-18 still hold for these rows (pinned by `tests/staff-caused-session-revocation.test.js`): a replay of a staff-ended session's own last refresh token is refused but recorded nowhere; the staff-side record is best effort, and when a marker cannot be read the sessions are still revoked for the staff reason with nothing recorded; a handoff retry on a staff-ended session still writes "Session reuse detected"; the older admin "delete user" flow (`admin_deleted`) is not covered.
- **A member staff deactivated stays deactivated** until the organization's own Owner or Admin reactivates them with `POST /api/organization/members/:userId/reactivate` (the member is listed as `deactivated` with the `version` to send). That makes the member active, clears `suspendedByStaff` with the suspension, and writes the customer's usual `organization.member.reactivated` event; from then on the member's sessions are the organization's own again. Staff can no longer reactivate a member. A pending flag that a member of the organization sets again is theirs: setting it clears `sessionRevocationStaff`. No marker is returned by any API.

### Staff organization block

`routes/adminOrganizationBlockRoute.ts`, `controller/adminOrganizationBlockController.ts`, service `src/modules/staffAccess/application/manageOrganizationBlock.ts`, store `infrastructure/mongoOrganizationBlockStore.ts`; the rule and the lookup are `src/modules/organizationBlock/` (`domain.ts`, `organizationBlockGate.ts`). Owner's decision, 2026-11-18 (`DECISIONS.md`): RFPilot staff block a whole customer organization and reactivate it. A block closes member sign-in and sessions, the organization's public links and its background work. Data is kept and everything works again on reactivate. Merged (backend PR #151) and on the `production` branch as of 2026-11-25; the admin app has block and reactivate screens and the dashboard shows a message for `ORGANIZATION_BLOCKED`. The security review of 2026-11-19 found no critical or high problem and no lock-out path; its findings are fixed or listed under "Known limits" (fix round, same PR).

| Route (under `/api/v1/admin/organizations/:organizationId`) | Body | `data` |
|---|---|---|
| `POST /block` | `{ reason }` | `{ organizationId, changed, blocked: true, blockedAt, sessionsEnded }` |
| `POST /reactivate` | `{ reason }` | `{ organizationId, changed, blocked: false, blockedAt: null }` |

- Who, organization and ids: as the staff reads above (`authenticate`, a staff membership role, and an `admins` account with role `admin`, `super_admin` or `superadmin`; the organization only from the path, 24 lower-case hex). `reason`: required, text, trimmed, 10 to 500 characters, otherwise 400 `INVALID_REASON` with `fields: { reason: "<message>" }`; stored on the staff-side event only and never returned. Rate limit: **60 writes per 15 minutes per staff account** (`organization-member-write`, `staffMemberWrites` in `routes/adminOrganizationMembersRoute.ts`; block and reactivate are now its only users). These are the only staff routes under `/admin/organizations/:organizationId` that are not a GET.
- Idempotent: blocking a blocked organization, or reactivating one that is not blocked, answers 200 with `changed: false` and is still recorded. A repeated block also ends any session of the organization that began while the first block committed.
- Refusals: 400 `INVALID_ORGANIZATION_ID`, 400 `INVALID_REASON`, 404 `ORGANIZATION_NOT_FOUND`, 409 `ORGANIZATION_NOT_MANAGEABLE` (`standing: "platform"` for RFPilot's own organization or any organization holding `admins` accounts, `"legacy_holding"` for a holding tenant: neither can ever be blocked), 403 `STAFF_ACCESS_FORBIDDEN`, 429, 500 `STAFF_ORGANIZATION_BLOCK_INTERNAL_ERROR`.
- **Reactivating is allowed for any organization that carries the marker.** It only removes a marker, so an organization that was blocked as a customer organization and stopped being manageable afterwards (an `admins` account added, its kind changed) is still reactivated through the route: staff-guarded, with a reason, recorded on the staff side with `standing` in the event. Blocking keeps the full rule, and reactivating an unmanageable organization that carries no marker is refused as before (409).
- **The marker.** A block is `blocked: { at, byStaffOrganizationId, byStaffAccountId }` on the organization document, with no schema default; reactivating removes the field. An organization is blocked when, and only when, `blocked.at` is a real date (`isOrganizationBlocked`). `Organization.status` is **not** used: `inactive` is written by a placement rollback and still enforces nothing. Every organization document without the field, which is every organization staff never blocked, is not blocked.
- **One transaction.** The marker, the ending of every live session of that organization (revoke reason `staff_organization_blocked`) and the staff-side event commit together, or none of them does.
- **Audit (staff side only).** After the staff-account check every request leaves exactly one `SecurityAuditEvent` in the **staff** organization: `platform.organization.blocked` or `platform.organization.reactivated`, `decision` `allowed` (a change, or nothing to change) or `denied` (a refusal; best effort), with the customer organization as target, `changed`, before and after, `sessionsEnded`, the reason and the staff account. **The block causes no row in the customer organization's audit trail**, when it is set or afterwards: the access path ends a blocked member's sessions through the session repository (no `auth.sessions.revoked_all`), a refresh refused for the block records nothing, and a session the block ended writes no `auth.refresh.reuse_detected` when its last token is presented again, also after a reactivation. What a person does with a credential that was already dead (below) is recorded exactly as it is without a block, because it is not caused by the block: the reuse of a consumed or logged-out refresh token, and the ending of a still-live session of a member who is no longer active. An access request is the requester's own action and writes its usual `organization.access_request.created` row.
- **Where staff see it.** `GET /api/v1/admin/organization-plans`, `GET /api/v1/admin/organization-plans/:organizationId` and `GET /api/v1/admin/organizations/:organizationId` carry `blocked: true` and `blockedAt` on the organization **only while it is blocked**; for an organization that is not blocked their answers are unchanged (no `blocked` key means not blocked). None of them says which staff account blocked it: that is in the staff organization's audit trail.
- **Not cached.** Every enforcement point reads the organization document by id when it acts (the access path reads it anyway), so a block and a reactivation apply on the next request or job on every API instance, worker and cron process. A failed read never answers "blocked" or "not blocked": the request fails (or the job is deferred), as it would have without this feature, since every such surface needs MongoDB for its own work.

**What a member of a blocked organization gets** (the dashboard shows a plain message for the code; no screen is built here):

| Where | Answer |
|---|---|
| Any authenticated request (`authenticate`, including the upload ticket) | 401 `{ code: "ORGANIZATION_BLOCKED", message }` for an active member whose session is live or was ended by the block; 401 like `MEMBERSHIP_INACTIVE` and `ORGANIZATION_SETUP_REQUIRED`, so the client drops the session |
| `POST /api/auth/refresh` | 401 `{ code: "REFRESH_SESSION_EXPIRED", reason: "organization_blocked" }` for a refresh that would otherwise have been granted, and for the current token of a session the block ended |
| Sign-in after the identity is proven: `POST /api/auth/login`, `/api/auth/google`, `/api/auth/2fa/challenge` and `/enrolment/confirm`, `/api/auth/sso/exchange`, an invitation accepted a moment before the block | 403 `{ code: "ORGANIZATION_BLOCKED", errorCode: "ORGANIZATION_BLOCKED", message }`; no session, no cookie, no two-factor challenge |
| `GET /api/auth/sso/callback` (company or Microsoft) | redirect to the sign-in page with `?error=ORGANIZATION_BLOCKED`; no account is linked or joined (a Microsoft identity is not linked to an existing account either: the organization is asked before the link) |
| Notification socket | 401 on upgrade |

The message is "Your organization's access to RFPilot is paused. Contact RFPilot support." A person whose account belongs to another organization is not affected: the block is asked about the organization of the session being begun or used, never about the person.

**A dead credential is not told.** The block is decided only where the request would otherwise have been let through, so a person whose credential no longer works for its own reasons gets the answer they always got and does not learn that the organization is blocked:

| Credential | Answer in a blocked organization (the same as in any other) |
|---|---|
| Access token of a removed or deactivated member | 401 `MEMBERSHIP_INACTIVE` |
| Access token of an account waiting for placement (`legacy_holding`) | 401 `ORGANIZATION_SETUP_REQUIRED` |
| Access token of a blocked or missing account, or of a session that was logged out, revoked for another reason, or expired | 403 `Active organization membership required` |
| Refresh token that was consumed (rotated away), or of a logged-out or otherwise revoked session | 401 `reason: "reuse_detected"` |
| Refresh token of an expired session; of a member who is no longer active; one never issued | 401 `reason: "expired"`; `"membership_inactive"`; `"invalid"` |

Order of checks in `authenticate`: token, then membership (missing or not active), then `legacy_holding`, then account and live session, then the organization exists, **then the block**, then the request goes on (the pending role-change revocation is not reached for a blocked organization). A session the block itself ended counts as the live session it was (read only for a blocked organization), so a live member is told `ORGANIZATION_BLOCKED` rather than 403. In the refresh path the gate is asked last at the two places that issue tokens (the direct rotation and a recoverable handoff retry).

**What a vendor or an invited person gets: the answer of a link that does not exist.** Nothing says the organization is blocked.

| Surface | Answer while blocked (the same as for an unknown link) |
|---|---|
| Every route behind `requirePublicGrant`: vendor workspace, receipts, drafts (create, read, save, upload, delete), finalize, revision drafts; the shared and public proposal page and its view counter | 403 `Access grant is invalid, expired, revoked, or exhausted`. The link is not used: no use is counted |
| `POST /api/v1/invitations/lookup` and the three accept routes; an invitation followed through Microsoft or company sign-in | 404 `INVITATION_INVALID`. The invitation is untouched |
| The "your company already uses RFPilot" answers at sign-up: `POST /api/auth/verify-otp` (`organizationMatch`), `POST /api/auth/register` and Google sign-in (409 `ORGANIZATION_DOMAIN_MATCH` unless the body has `separateOrganization: true`), a first Microsoft or company sign-in (`error=ORGANIZATION_DOMAIN_MATCH`) | **unchanged**: a blocked organization's domain matches exactly as when it is not blocked, so a sign-up on its domain does not silently get a separate organization (owner's decision, 2026-11-19) and an outsider sees no difference. Choosing a separate organization stays the person's own explicit choice |
| `POST /api/auth/access-requests` | 201 `{ status: "pending", organizationName }`, as for any pending request. The request is stored; **auto-approve does not run** (no invitation is created or emailed), and the organization's Owners and Admins get **no notification and no email**. The one accepted tell: `pending` where an auto-approve domain would have answered `invited`. After a reactivation the request is in the Owners' and Admins' list and they approve or deny it; no late notification is sent and auto-approve is not applied to it afterwards |
| `GET /api/emails/open/:trackingId`, `/click/:trackingId`, `/vendor-click/:trackingId` | the pixel, or the fallback redirect; nothing is recorded |
| `POST /api/auth/sso/discover`, `GET /api/auth/sso/start` | **unchanged on purpose**: they answer anyone who types an email, so they must not change with a block |

**Background work is paused, not dropped.**

| Work | While blocked | After reactivation |
|---|---|---|
| Every durable job type (`source_security_scan`, `knowledge_parse`, `knowledge_index_release`, `proposal_context_extract`, `candidate_application`, `proposal_draft_generate`, `vendor_response_analyze`, `vendor_source_extract`, `vendor_requirement_facts`, `comparison_participant_snapshot`, `comparison_aggregate`, `conversation_chat`, `ai_gateway_test`) | **Deferred**: before the job is claimed the worker moves it back to BullMQ's delayed set for 5 minutes and asks again. Not run, not claimed, no attempt counted, never failed or dead-lettered. The PostgreSQL job row stays `queued`. A job that was **already running** when the block committed is not stopped: it finishes (see "Known limits") | Runs at its next turn, at most 5 minutes later |
| Proposal expiry and "expires tomorrow" notices | **Paused** (skipped) | The next run (12 hours, and at start-up) applies them; a proposal whose date passed during the block expires then |
| Purge of proposals archived for 30 days; retention sweep; vendor draft cleanup | **Paused**: nothing of the organization is deleted | The next daily run treats it like any other |
| Invitation expiry, day-six reminder, invitation email retries | **Paused**: nothing is expired, reminded or emailed | The next 15-minute pass; an invitation whose own expiry date passed is expired then (a block does not extend it) |
| Domain re-verification | **Paused**: no domain is un-verified | Checked on the next pass |
| Support ticket auto-close reminder, auto-resolve, auto-close | **Paused** for the organization's tickets | The next 5-minute pass |
| Support ticket escalation to RFPilot staff | **Not paused**: it is addressed to staff | |
| Orphaned-proposal count | **Not paused**: read-only, writes nothing | |

**Sweeps are fair to the other organizations.** The limited, oldest-first sweeps (vendor draft cleanup, the three support ticket steps, domain re-verification, the invitation reminder and email retries) leave blocked organizations out **in the query**, so a blocked organization's rows, which stay due for as long as the block lasts, cannot fill a batch and starve everyone else. The dispatcher's reconcile pass does the same for queued jobs when its process has a MongoDB connection (`MONGODB_URL` set; optional, never fatal; if MongoDB was unreachable when the dispatcher started, each reconcile pass starts a new attempt without waiting for it, and logs a failure at most once a minute); without one it reconciles every organization as before, and a blocked organization with more queued jobs than the batch (200) can then delay the Redis-loss recovery of other tenants.

**Both workers require MongoDB.** The durable worker and the AI gateway worker await the MongoDB connection before they take jobs (the block is read there), and exit non-zero with one line naming the cause when `MONGODB_URL` is missing (at once) or MongoDB cannot be reached at start-up (after 5 attempts with 5, 10, 15 and 30 seconds between them, so a short outage during a deploy does not fail the task). Before, `start:worker` connected only when a capability that needs MongoDB was enabled. A MongoDB outage after start-up does not stop a worker: jobs are deferred 30 seconds and asked again.

**Staff keep working on a blocked organization.** Staff requests authenticate against the staff organization, and the staff reads above answer for a blocked organization as for any other. The block route refuses the caller's own organization, any organization `admins` accounts belong to and any organization that is not a customer organization (409 `ORGANIZATION_NOT_MANAGEABLE`), so staff cannot block the organization they sign in to. That is a rule of the route, not of the marker: an organization blocked while it was a plain customer organization and later made one of those keeps its marker and is treated as blocked like any other (one rule, `isOrganizationBlocked`, for every organization), and `POST /reactivate` removes a marker whatever the organization is now.

**Known limits.** (1) Files under the legacy `/uploads` static path are served by file name with no organization in the path, so a block cannot close them; production stores uploads in private object storage. (2) A response stream or notification socket already open when the block commits is not cut; it ends with the request, and no new one can be opened. (3) With `PUBLIC_GRANTS_ENFORCED=false` (never honoured in production) public links are not checked at all, so neither is the block. (4) A two-factor challenge issued in the minutes before the block can still be answered (it changes only the member's own two-factor state); the session it would lead to is refused. (5) A wrong-password attempt on a member's account is still recorded in the organization as before: it is not staff activity. (6) The operator scripts under `scripts/` (purges, backfills) do not ask about the block. (7) **Not yet: a job already running when the block commits runs to completion.** The worker asks the gate once, before it claims the job; it does not ask again at lease renewal, because stopping a handler part-way could leave its writes half done. So "nothing runs for a blocked organization" is true of every job that had not started; a job in flight finishes (minutes at most) and may write its result. (8) An access request on a blocked organization's auto-approve domain answers `pending` where it would answer `invited`: the one difference an outsider can see. (9) The dispatcher's reconcile exclusion needs `MONGODB_URL` on the dispatcher (above). (10) The dispatcher's reconcile exclusion of blocked organizations is proven only under a PostgreSQL login that bypasses row-level security, as the integration suite uses: the statement reads `rfpilot.organizations` for every tenant in one query. What login production's dispatcher uses was not checked; under a login that row-level security applies to, the exclusion may leave nothing out (reconcile would then run as it did before, for every organization).

`tests/organization-block-guard.test.js` fails when a new route, server surface, worker, timer or scheduled job acts for an organization without going through the block check or being listed there with its reason; its header lists what it does not catch.

### Staff client list (`/api/all-clients`)

`routes/allClientsRoute.ts`, `src/modules/admin/application/manageAdminClients.ts`. The admin app's Clients page. It lists the `users` accounts in the **signed-in staff member's own organization** whose account role is not administrative; that organization is the shared one that still holds legacy customers until the tenancy cutover. It never reads another organization.

- Who: `authenticate` plus a staff membership role (`dxg_admin` or `super_admin`), and the controller requires an administrative account role. Customers get the route guard's plain 403. Block and delete need `super_admin`.
- `GET /` `?search=&page=`, 10 per page, newest account first; `search` matches name or email. Answers `{ success, message, data: [client], pagination: { page, perPage, total, totalPages, hasNextPage, hasPrevPage }, filters: { search } }`.
- A client is an allowlist built field by field: `{ id, name, email, company, joinDate, isBlocked, totalProposals, totalEmailSent }`. Nothing else a query returns can reach the response.
- `totalProposals` is a **number**: how many proposals the account owns in the staff member's organization. It is account-level usage, which staff may see without a support grant (DECISIONS, 2026-11-17); no proposal title, id or other content is returned or loaded.
- `totalEmailSent` is a **number**: the sum of `sentCount` over the account's email campaigns in the staff member's organization. No campaign subject, recipient or other content is returned or loaded.
- Both numbers come from one grouped query each (`src/modules/admin/infrastructure/mongo/accountUsageCounts.ts`), on `Proposal` and on `EmailCampaign`, filtered by `organizationId` (the session's organization) and the listed account ids. A proposal or campaign the same account id owns in any other organization is not counted. A row with no `organizationId` at all is not counted either: that is an undercount, never a leak. `tests/tenant-scope-guard.test.js` covers the proposal query.
- Audit: none. Like the organization-plans list, the list writes no audit event, in the staff organization or anywhere else.
- `PATCH /:id/block` `{ isBlocked: boolean }` and `DELETE /:id` act on an account in the staff member's own organization only; another organization's account is 404, and an administrative account is 400.

### Admin overview (`GET /api/admin/overview`)

`routes/adminRoute.ts`, `src/modules/admin/infrastructure/mongo/mongoAdminOverviewReadRepository.ts`. The admin app's dashboard. Same guard as the staff client list, and the same boundary: numbers about the signed-in staff member's own organization, no customer content, no audit event. It is the only route left on the `/api/admin` router besides legacy-customer placement.

- Answers `{ success, message, data: { totals: { totalClients, totalProposals, totalEmailSent, totalClick }, latestClients: [{ id, name, email, company, joinDate, totalProposals, totalEmailSent }] } }`. `latestClients` is the 10 newest non-administrative `users` accounts in that organization.
- Every number is counted with `organizationId` in the filter. The per-account `totalProposals` and `totalEmailSent` in `latestClients` are the same two queries the staff client list uses, so the dashboard and the Clients page agree for the same account, and what an account owns in another organization (or with no `organizationId`) is not counted.

## Organization vendor list (ORG-606)

`routes/organizationVendorsRoute.ts`, rules in `src/modules/organizationVendors/application/manageOrganizationVendors.ts`. One shared list of vendor companies and contacts per organization (DXG decision Q4), for picking recipients when sending an RFP. Every route here needs a signed-in member and acts on the caller's own organization only; another organization's vendor is 404 `VENDOR_NOT_FOUND`. No route accepts a public access grant, so a vendor's submission link never reaches the list. RFPilot staff can view the list, read-only, at `GET /api/v1/admin/organizations/:organizationId/vendors` (owner's decision, 2026-11-17; "Staff access to an organization's content"). Roles (`authorizationPolicy.ts`): `vendor-list:write` for Owner, Admin and Team Manager; `vendor-list:read` for those plus Planner; a Viewer gets 403 on every route.

A vendor is `{ id, company, category, contacts: [{ name, email }], addedBy, archived, archivedAt, createdAt, updatedAt }`.

- `GET /api/v1/vendor-list?search=&category=&status=active|archived|all&limit=&offset=` returns `{ items, total, limit, offset }`, sorted by company. `search` matches part of the company or the category, ignoring case; `category` is an exact match, ignoring case. `status` defaults to `active`; `limit` defaults to 50 (max 200). Any other `status` is 400 `INVALID_VENDOR_STATUS`.
- `GET /api/v1/vendor-list/categories` returns the distinct categories of active vendors, as `string[]`.
- `GET /api/v1/vendor-list/:vendorId` returns one vendor, archived or not. A malformed id is 404, like a missing one.
- `POST /api/v1/vendor-list` `{ company, category?, contacts? }` adds a vendor (201). `company` is 1 to 200 characters, `category` free text up to 80, `contacts` up to 50 `{ name?, email }` with a valid email, each email once per vendor (400 `INVALID_VENDOR_COMPANY`, `INVALID_VENDOR_CATEGORY`, `INVALID_VENDOR_CONTACTS`, `INVALID_VENDOR_CONTACT_EMAIL`, `DUPLICATE_VENDOR_CONTACT_EMAIL`). Emails are stored in lower case. Active company names are unique per organization, ignoring case (409 `VENDOR_COMPANY_TAKEN`).
- `PATCH /api/v1/vendor-list/:vendorId` changes only the fields sent; `contacts` replaces the whole list (`[]` removes every contact; `null` is 400), and `category: ""` clears the category. Two people editing the same vendor at once: the last write wins. An archived vendor can't be edited (409 `VENDOR_ARCHIVED`).
- `POST /api/v1/vendor-list/:vendorId/archive` and `/restore` take a vendor off the default list and put it back. Both are idempotent. Restoring is 409 `VENDOR_COMPANY_TAKEN` when an active vendor has taken the name. There is no hard delete.
- Each add, edit, archive and restore writes a `SecurityAuditEvent` with `targetType: "organization_vendor"` (`organization_vendor.created`, `.updated`, `.archived`, `.restored`). The metadata records which fields changed and the contact count, never contact names or emails.

## RFP templates (ORG-604)

`routes/proposalTemplatesRoute.ts`, rules in `src/modules/proposalTemplates/application/manageProposalTemplates.ts`, snapshot rules in `src/modules/proposals/domain/templateSnapshot.ts`. A template is a snapshot of an RFP's content and presentation layout that members start new RFPs from (DXG decision Q4). Every route needs a signed-in member and acts on the caller's own organization only; no route accepts a public access grant. Responses are `{ success, data }`, errors `{ success: false, code, message }`; a role refused at the route (a Viewer anywhere, a non-manager on publish and unpublish) gets the shared 403 `{ success: false, message }` with no `code`.

Roles (`authorizationPolicy.ts`): `template:use` (Owner, Admin, Team Manager, Planner) lists and opens templates, saves personal ones and starts RFPs from them; `template:publish` (Owner, Admin) also manages organization templates. Viewers are refused on every route (403). Who sees what:

- A **personal** template is visible to the member who saved it and to nobody else, whatever their role.
- An **organization** template is visible to every `template:use` member while it is published and not archived. Unpublished or archived, only Owners and Admins see it.
- Another organization's template is 404 `TEMPLATE_NOT_FOUND`, the same answer as a missing or malformed id. A template in the caller's organization that they may not see is 403 `TEMPLATE_ACCESS_DENIED` (the RFP convention: in the organization but out of scope is 403).

A template is `{ id, title, description, scope: "personal"|"organization", presentationLayout: "template-one"|"template-two"|null, published, publishedAt, publishedBy, ownerUserId, ownedByMe, usable, archived, archivedAt, eventName, createdAt, updatedAt }`; the detail routes add `content`. `usable` says whether an RFP can be started from it now (not archived, and personal or published).

- `GET /api/v1/proposal-templates?scope=personal|organization|all&status=active|archived|all&search=&limit=&offset=` returns `{ items, total, limit, offset }` without `content`, sorted by title. Defaults: `scope=all`, `status=active`, `limit=50` (max 200). `search` matches part of the title or description, ignoring case. Any other `scope` or `status` is 400 `INVALID_TEMPLATE_SCOPE` / `INVALID_TEMPLATE_STATUS`.
- `GET /api/v1/proposal-templates/:templateId` returns one template with `content`.
- `POST /api/v1/proposal-templates` `{ proposalId, title, description?, scope?, presentationLayout? }` saves an RFP as a template (201). The caller needs view access to the RFP: one outside the organization is 404 `TEMPLATE_SOURCE_NOT_FOUND`, one in the organization that they can't see is 403 `PROPOSAL_ACCESS_DENIED` ("You don't have access to this RFP."). `scope` defaults to `personal`; `organization` needs `template:publish` (403 `TEMPLATE_PUBLISH_DENIED`) and publishes at once. `title` is 1 to 120 characters, `description` up to 500 (400 `INVALID_TEMPLATE_TITLE`, `INVALID_TEMPLATE_DESCRIPTION`, `INVALID_TEMPLATE_SCOPE`, `INVALID_TEMPLATE_LAYOUT`, `INVALID_TEMPLATE_SOURCE`). The RFP does not store which presentation layout it uses, so the client sends `presentationLayout`. The snapshot keeps the sections `event`, `venueSchedule`, `roomByRoom`, `production`, `hybridVirtual`, `contentCreative`, `venue` and `budget`, minus every key that names a date or schedule time, a contact person, an uploaded file, a co-vendor or the venue's in-house AV company name (`inHouseAvRequired` stays). It never holds the contact section, uploads, vendors, responses, status, lifecycle, team or owner. A snapshot over 512 KB is 413 `TEMPLATE_TOO_LARGE`. Saving a template uses no plan slot.
- `PATCH /api/v1/proposal-templates/:templateId` `{ title?, description? }` renames it. The snapshot never changes after it is saved. An archived template is 409 `TEMPLATE_ARCHIVED`.
- `POST /api/v1/proposal-templates/:templateId/publish` (Owner, Admin) makes one of the caller's own personal templates, or an unpublished organization template, an organization template in the picker. `POST …/unpublish` takes it out of the picker; it stays an organization template that Owners and Admins can publish again. Both are idempotent. Publishing an archived template is 409 `TEMPLATE_ARCHIVED`.
- `POST /api/v1/proposal-templates/:templateId/archive` and `/restore`: a personal template by its owner, an organization template by Owner or Admin (otherwise 403 `TEMPLATE_PUBLISH_DENIED`). Archiving also unpublishes, so a restored organization template is unpublished until someone publishes it again. Both are idempotent. There is no hard delete.
- `POST /api/v1/proposal-templates/:templateId/proposals` `{ eventName? }` starts a new RFP from the template (201, `data` is `{ proposal, presentationLayout }`: the RFP in the same shape as `POST /api/proposals`, and the template's layout for the client to apply, because the RFP record has no layout field). The route also needs `proposal:write`. The RFP is an unsubmitted draft owned by the caller, on the caller's team when they're on exactly one (ORG-202), with the template's content and no dates, contacts, vendors or files; nothing else in the body is read. Without `eventName` (up to 200 characters, 400 `INVALID_TEMPLATE_EVENT_NAME`) it takes the template's event name, then its title. It counts toward the plan limit like any new RFP: 403 `PLAN_LIMIT_REACHED` (ORG-601 body) at the limit. For a member who can see it, an archived template is 409 `TEMPLATE_ARCHIVED` and an unpublished organization template 409 `TEMPLATE_NOT_PUBLISHED` (Team Managers and Planners can't see either, so they get 403 `TEMPLATE_ACCESS_DENIED`).
- Each save, rename, publish, unpublish, archive and restore writes a `SecurityAuditEvent` with `targetType: "proposal_template"` (`proposal_template.created`, `.updated`, `.published`, `.unpublished`, `.archived`, `.restored`). The metadata carries the title and scope, never the snapshot. These actions are not in the audit view's catalog yet (see "Organization audit log"), so they are stored but an Owner or Admin does not see them at `/settings/audit`.

## Legacy customer placement

ORG-110, DXG admins only, at `/api/admin/legacy-customers` (`routes/adminLegacyCustomersRoute.ts`, `src/modules/tenancy/legacyCustomerPlacement.ts`; the task path is `placementTasks.ts`, `placementTaskLauncher.ts` and `placementTaskRunner.ts` beside it).

- `GET /` lists the legacy customers not yet placed, with each one's RFP count. `GET /target-organizations?q=` searches the organizations a customer can be placed in.
- `POST /:userId/placements` `{ target: "new", organization }` or `{ target: "existing", organizationId, role, teamId? }`. `teamId` must be an active team of that organization (400 `UNKNOWN_TEAM`). A second placement of the same user while one runs is 409 `PLACEMENT_IN_PROGRESS`.
- `POST /placements/:runId/rollback` is refused with 409 `PLACEMENT_IN_PROGRESS` until the placement's own task has finished (see `status` below). It moves back exactly the records the run moved (journaled ids); RFPs given to the user afterwards stay and are counted in `leftInTarget`. One rollback runs at a time (409 `ROLLBACK_IN_PROGRESS`, `ALREADY_ROLLED_BACK`); 409 `NOTHING_TO_ROLL_BACK` for a run that moved nothing, `ORGANIZATION_IN_USE` and `USER_IS_OWNER` when the organization has moved on.
- Until placed, the account can't use RFPilot: every sign-in method answers 403 `ORGANIZATION_SETUP_REQUIRED` (after the password or identity check, before 2FA), and any request on an existing session answers 401 `ORGANIZATION_SETUP_REQUIRED` and revokes all of that account's sessions.

**How a placement runs depends on the server (decision 2026-11-17).** Moving Postgres rows between organizations needs the table-owner role (`POSTGRES_MIGRATION_URL`), which the public API never holds in production.

- **Production: in a separate task, asynchronously.** The API validates the request exactly as below (same refusals, same codes), records it as a queued run and starts an execution of the placement state machine (Step Functions), passing only the run id. The state machine runs the placement task, whose definition, network and command are fixed; the API has no permission to start or alter a task itself. Both `POST`s answer **202** `{ placement, replayed }` and the client polls `GET /placements/:runId`. Nothing moves inside the API process.
- **Local stack, rehearsal, integration suite** (the process has `POSTGRES_MIGRATION_URL`, or the Postgres foundation is off): synchronously, inside the request. `POST /:userId/placements` answers 201 `{ placement }` with the result; a failure leaves nothing moved (409 `PLACEMENT_FAILED`), and a run whose ORG-109 checks fail is rolled back at once and answers 409 `PLACEMENT_VERIFICATION_FAILED` with `details.verification` and `details.rolledBack`. Rollback answers 200 `{ rollback }`, or 409 `ROLLBACK_CONFLICT` when Postgres rows created since still depend on the user's rows.
- **Neither** (no migration role and no `PLACEMENT_STATE_MACHINE_ARN`): 503 `PLACEMENT_REQUIRES_MIGRATION_ROLE`. Unsetting that variable on the API is how the task path is switched off. A value that is not the placement state machine's ARN: 503 `PLACEMENT_TASK_MISCONFIGURED`.
- **Who may call these routes, in both modes.** A staff membership role and an account in the `admins` collection with a staff account role, as for plan management and support access. A customer gets the route guard's plain 403; a `users` account that holds a staff membership role gets 403 `PLACEMENT_FORBIDDEN` on all five routes. A staff account with no organization is refused with 403 `STAFF_ORGANIZATION_REQUIRED`. Each staff member has three allowances per 15 minutes: 1,500 reads of a run (`GET /placements/:runId`), 600 reads of the two lists, and 120 placement or rollback requests. Past one, 429 `PLACEMENT_RATE_LIMITED` with `Retry-After` (seconds until the window resets). That is a different refusal from 429 `PLACEMENT_CAPACITY_REACHED`, which means another placement is running. **A screen that polls a run should do so every 3 seconds or slower** (300 reads per tab per window), and stop when `status` is no longer `queued` or `running`.

`GET /placements/:runId` (404 `PLACEMENT_NOT_FOUND`) returns the run in both modes: the journal fields (`runId`, `userId`, `holdingOrganizationId`, `targetOrganizationId`, `createdOrganization`, `role`, `teamId`, `state`, `mongo`, `postgres`, `verification`, `leftInTarget`, `error`) plus the fields below. `error` and `task.message` are sentences written for staff; a database or driver error is never returned, only logged.

| Field | Meaning |
|---|---|
| `status` | `queued` (task not started yet), `running`, `succeeded` (the customer is placed and ORG-109's checks passed; if the task failed or was lost after that point, `task.status` is `failed` and `task.details.auditUnconfirmed` is true), `failed`, `rolled_back`. A placement stays `running` until its task has finished, even though `state` turns `done` as soon as the MongoDB move commits: the Postgres commit, the checks and the audit events come after that. While a rollback is queued or running, `status` is `queued` or `running` and `operation` is `rollback`. |
| `operation` | `placement` or `rollback`: what `status` describes. |
| `rollbackRequired` | `true` when the customer's records are in the target but the run did not finish cleanly: MongoDB moved and Postgres did not, the task stopped before its checks ran, or the checks failed and the automatic rollback failed too. `status` is then `failed`. Roll the run back before doing anything else with that customer. |
| `task` | The latest task for the run, or `null` for a run made synchronously: `{ operation, status: queued\|running\|succeeded\|failed, requestedAt, startedAt, heartbeatAt, finishedAt, code, message, details }`. `code` is the failure code. A rollback that fails leaves `status: "succeeded"` (the placement stands) with `task.operation: "rollback"`, `task.status: "failed"`. No AWS identifier or AWS error text is returned; those are in the server log. |

Failure codes a task reports in `task.code` (the synchronous path returns the same codes as HTTP errors):

- the request-time refusals again if the data changed before the task ran (`NOT_A_LEGACY_CUSTOMER`, `ORGANIZATION_NOT_FOUND`, `ALREADY_A_MEMBER`, `UNKNOWN_TEAM`, …);
- `PLACEMENT_FAILED`: nothing moved, unless `rollbackRequired` is true;
- `PLACEMENT_VERIFICATION_FAILED` with `details.verification` and `details.rolledBack`. When `rolledBack` is true the run's `status` is `rolled_back`. When it is false the automatic rollback failed: `status` is `failed`, `state` is `failed` and `rollbackRequired` is true;
- `ROLLBACK_CONFLICT`, `ORGANIZATION_IN_USE`, `USER_IS_OWNER`: the rollback was refused and the placement stands;
- `PLACEMENT_REQUEST_INVALID`: the task did not accept the queued request. It checks the request again rather than trusting the journal: the staff member must still be an unblocked `admins` account with a staff membership in their organization, and a rollback must be from a customer organization the person is a member of to that person's own holding tenant. Nothing moved;
- `PLACEMENT_TASK_ERROR` / `ROLLBACK_TASK_ERROR` for anything unexpected (see the task's log). If a placement task fails this way after the move has committed, what the run reads depends on its checks: if they had not passed (or never ran), `status` is `failed`, `state` is `failed` and `rollbackRequired` is true; if they had passed and only the audit write failed, `status` stays `succeeded` with `task.details.auditUnconfirmed`. The same rule applies when the task is lost instead of failing;
- `PLACEMENT_TASK_SUPERSEDED`, `PLACEMENT_TASK_RESULT_NOT_RECORDED`: the task found the run was no longer its own (the API had given up on it) and stopped. These appear in the task's log and exit code; the run shows what the API recorded when it gave up.

Task-mode rules:

- **One at a time.** One placement or rollback per user (409 `PLACEMENT_IN_PROGRESS` / `ROLLBACK_IN_PROGRESS`), and `PLACEMENT_TASK_MAX_CONCURRENT` tasks in total (default 1, because a placement takes exclusive Postgres locks on a live product): past that, 429 `PLACEMENT_CAPACITY_REACHED` with `Retry-After: 30`. Both are unique indexes on the placement journal, so they hold across API instances.
- **`Idempotency-Key`** (optional header, 1 to 200 printable characters; else 400 `INVALID_IDEMPOTENCY_KEY`). The key belongs to the staff member who sends it. Repeating a request with the same key returns the same run with `replayed: true` and starts no second task, while that run is queued or running and after it has finished with anything moved (`succeeded`, `rolled_back`, or `failed` with `rollbackRequired`). A run that ended with **nothing moved** (the task could not be started, never started, or refused or failed before moving anything) gives the key back, so the same key then starts a new run instead of replaying the failure. The same applies to a rollback whose task failed. The same key on a different request is 409 `IDEMPOTENCY_KEY_REUSED`. Without a key, a repeat while the run is active is the 409 above.
- **A task that can't be started** answers 503 `PLACEMENT_TASK_START_FAILED` / `ROLLBACK_TASK_START_FAILED` with `details.runId`; nothing moved and the request can be made again.
- **A stuck task is given up on when a run is read or a new request arrives.** A task that hasn't started 4 minutes after the request fails with `PLACEMENT_TASK_NOT_STARTED` / `ROLLBACK_TASK_NOT_STARTED`. A running task writes a heartbeat every 15 seconds; one silent for 3 minutes fails with `PLACEMENT_TASK_LOST` / `ROLLBACK_TASK_LOST`. Nothing moved unless `rollbackRequired` is true; `task.details.needsOperatorCheck` marks the one case an operator must look at: a rollback whose MongoDB half finished (`state: rolled_back`) but whose task then failed or was lost, so Postgres may not have been moved back. A placement task lost after the move was made and its checks passed (`verification.passed`) leaves the run `succeeded` with `task.details.auditUnconfirmed`: the placement stands, and only its audit events may be missing. What is guarded, exactly: the MongoDB move's commit requires the journal to still say `started`, and giving up on a task moves that state on, so a task that was given up on cannot commit the move. After that commit, each of the task's journal writes (a failed Postgres commit, its checks, claiming its own rollback) requires this task attempt and a task still marked running; one that matches nothing makes the task stop and exit non-zero. The task also stops itself after a minute without a heartbeat. The two timeouts can be changed with `PLACEMENT_TASK_START_TIMEOUT_SECONDS` (at least 60) and `PLACEMENT_TASK_HEARTBEAT_TIMEOUT_SECONDS` (at least 120); the API refuses to start with a value out of range. Runbook: [runbooks/ORG_TENANCY_CUTOVER.md](runbooks/ORG_TENANCY_CUTOVER.md), "Place legacy customers".
- **Audit.** A placement or rollback that completes writes the same audit events as the synchronous path (`organization.legacy_customer.placed` / `.placement_rolled_back` in the target organization and `admin.…` in the staff organization), written by the task and naming the staff member who made the request. A request that is refused, fails or is given up on writes **no** audit event, in either mode; the journal entry (`GET /placements/:runId`) and the API log lines `placement_task_started`, `placement_task_start_failed` and `placement_task_given_up` are its record.

Operators can still run `scripts/placeLegacyCustomer.js` by hand as a one-off task on the migrate task definition (`--list`; `--email --admin-email --new-org` or `--org-slug --role`; `--rollback=<runId>`; dry run unless `--apply`). That script and task definition are unchanged; the API cannot start them.

## Launch metrics (ORG-505)

`GET /api/v1/admin/launch-metrics?days=` returns the PRD success metrics for Organization Accounts as counts, rates and durations across all customer organizations (`routes/launchMetricsRoute.ts`, `src/modules/launchMetrics`). It carries no names, emails, ids or RFP content. Staff role and an `admins` account only: customers get the route guard's plain 403, and a member holding a staff role 403 `LAUNCH_METRICS_FORBIDDEN`. Each read writes a `platform.launch_metrics.read` audit event in the staff organization before anything is returned. `days` (1 to 365, default 30; otherwise 400 `INVALID_WINDOW`) is the window for the first three figures; the last two are as of now. `npm run report:launch-metrics -- [--days=30]` prints the same report for an operator with database access.

- `inviteAcceptance` `{ sent, atLeast7DaysOld, acceptedWithin7Days, acceptedLater, rate, target: 0.6 }`: of the invitations created in the `days`-long window that ended 7 days ago (so each has had its 7 days), the share accepted within 7 days of creation. Revoked and expired invitations stay in the denominator.
- `timeToFirstRfpOpened` `{ accepted, opened, notYetOpened, excludedOpenedBeforeAccepting, excludedAcceptedBeforeTracking, medianSeconds, openedWithin5Minutes, targetMedianSeconds: 300 }`: for invitations accepted in the window, the median time from acceptance to that member's first RFP opened in the organization (`OrganizationMembership.firstRfpOpenedAt`, stamped once by an authenticated `GET /api/proposals/:id`). Members who haven't opened one are counted, not timed. Acceptances from before the stamp existed (earlier than the earliest stamp on any membership) are counted in `excludedAcceptedBeforeTracking` and not timed, and a member invited back starts again from the new acceptance.
- `supportAccessUnderGrant` (**obsolete since 2026-11-17**: staff reads no longer need a grant and no longer write `support_access.used` or `.denied`, so this only counts rows written before then and will read zero for any later window; not removed in that change) `{ reads, underActiveGrant, withoutActiveGrant, refusedWithoutGrant, rate, target: 1 }`: of the `support_access.used` audit events in the window, the share whose `metadata.grantId` names a grant in the same organization that covers the target and was active at that moment. `reads` counts audit events (one per grant used), not HTTP requests. `refusedWithoutGrant` counts `support_access.denied` attempts, which returned no data.
- `organizationsWithTwoOrMoreActiveUsers` `{ organizations, withTwoOrMoreActiveUsers, rate, target: 0.25 }`: active organizations (not legacy holding tenants) with at least one active member in a customer role, and how many have two or more. Staff memberships don't count.
- `orphanedRfps` `{ total, organizations, target: 0 }`: RFPs whose owner is not an active member of the RFP's organization, from the same check the nightly job runs.
- A `rate` or `medianSeconds` is `null` when there is nothing to measure yet.
