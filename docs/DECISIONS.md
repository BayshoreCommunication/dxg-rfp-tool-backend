# Architectural Decisions

> Purpose: concise register of accepted, durable decisions. Last updated: 2026-11-10. Owner: engineering/product.

| Decision | Rationale / consequence |
|---|---|
| MongoDB remains proposal-content authority. | Avoids a destructive product migration; PostgreSQL references proposals and owns the AI domain. |
| The PostgreSQL identity projection is created at sign-in, not at signup (2026-08-10). | Nothing projected MongoDB accounts into `rfpilot.users`, so every new signup authenticated and then got 503 `ASSISTANT_ACTOR_NOT_READY` from the assistant, drafts, guidance and every other AI surface. Projecting in `beginAuthenticatedSession` covers all five auth entry points with one hook and also repairs accounts created earlier, on their next sign-in. The projection returns failures as outcomes instead of throwing, because an unavailable data foundation must degrade to "AI is off for now" rather than "you cannot sign in"; the AI modules already fail closed. It never reactivates a suspended organization or removed user, so revoked access cannot restore itself by signing in. `npm run backfill:identity-projections` repairs the existing population without waiting for sign-ins. |
| PostgreSQL owns durable AI state; Redis is transport only. | RLS, auditability, recovery, and reference-only queue messages. |
| Canonical `proposal.v1` contract with generated types. | One validated shape across API, AI, UI, and tests while legacy adapters preserve compatibility. |
| Canonical migration uses immutable snapshots, not in-place rewrites. | Dry-run, review, idempotency, and rollback without touching legacy records. |
| Vendor questionnaires are immutable, tenant-scoped MongoDB projections of canonical proposals (2026-09-14). | A deterministic projection exposes only vendor-safe fields and gives every room and specification a stable ID plus proposal source reference. Re-publishing the same source checksum is idempotent; a changed projection creates version `n + 1`, records the publishing actor, and supersedes the prior published version. The public workspace is an allowlisted DTO built from validated grant context, never from a raw token. |
| Vendor response drafts are grant-scoped, revisioned MongoDB working records with governed private documents (2026-09-14). | One active draft is allowed per tenant, proposal, and durable invitation ID. The record pins an immutable questionnaire snapshot and grant-subject hash but never stores the raw grant. Every save and document mutation uses compare-and-swap on `draftRevision`; stale requests fail with a deterministic conflict. Categorized files are checked against the pinned questionnaire, content-inspected, malware-scanned, and privately stored. Expiry and abandonment cleanup checks immutable submission versions before deleting an object and leaves provider failures retryable. |
| Structured vendor finalization uses a draft lock plus an immutable-version uniqueness boundary (2026-09-14). | Finalization claims one exact `draftRevision`, stamps acknowledgement times, performs final validation, verifies the active document manifest, and freezes the pinned questionnaire, structured response, deterministic calculation, and expanded manifest checksum. A unique sparse `finalizedDraftId` prevents a draft from creating two versions even when requests race or use different retry keys. Revision access is bound to the originating public grant, and inherited, added, and retired document dispositions preserve provenance without copying or deleting submitted objects. The latest version is still projected to `VendorResponse`, and source registration and notifications retain their existing compatibility behavior. |
| AI provider access uses a governed port and pinned model snapshot. | Provider replacement, deterministic release evidence, budget controls, and no hidden legacy endpoint. |
| Assistant-workspace extracted defaults apply automatically (2026-09-09). | Normalized, non-conflicting values attached to open guided fields are written through the canonical question-answer path without a separate confirmation click. Automatic writes fill empty targets only, remain visible with field-level Edit, and never publish or send the proposal. The separate governed candidate-review/application surface retains its explicit review controls. |
| Room recommendations are the one unattended application path. | Deterministic room suggestions fill **empty** allowlisted room fields without prior approval, so the planner adjusts values in the form instead of approving each. Bounded by: filled fields never overwritten, allowlisted paths only, crew appends only, version CAS plus per-room identity checks, and an audit row per application. Pending explicit DXG confirmation — see `architecture/ROOM_RECOMMENDATIONS.md`. |
| Human support is a separate in-app helpdesk; the AI Assistant is not the support channel (2026-10-18). | The client asked for "chatbot support" and clarified it as a CRM-style ticket inbox DXG answers from the admin app. The Platform Assistant stays exactly as shipped. The helpdesk is its own module (`src/modules/supportDesk`): MongoDB tickets/messages/canned replies, organization-scoped through the existing tenancy, planner routes under `/api/v1/support` for any active member and agent routes under `/api/v1/admin/support` for administrative roles only. Internal notes are stored as messages with `kind=internal_note` and are filtered out of every customer read path in the repository, not in the UI. Bell notifications fan out to all admins of the organization on customer activity and to the requester on agent activity; email is opt-in per environment. Unread counters live on the ticket so the sidebar badge is one count query. |
| An invitation link is the proof of email ownership for invited signup (2026-11-02, ORG-203). | The link reaches only the invited inbox, which is what the signup OTP proves, so `POST /api/v1/invitations/accept/register` creates the account with the invited email and no OTP, and joins it to the inviting organization without creating one of its own. So the link is guarded like a credential: 256-bit random, stored only as SHA-256, single use, seven days, rotated on every email (resend, retry, reminder), never logged or put in a URL path the API sees, and never copied to `SMTP_FIXED_RECIPIENTS`. Existing accounts must sign in with the invited email. Accounts active in another organization or still in a legacy holding tenant can't be invited or accept. |
| Two-factor is TOTP built on node:crypto, with seeds sealed under a dedicated key (ORG-303, 2026-11-02). | RFC 6238 is small enough to own and is pinned by the RFC test vectors, so no dependency was added. Seeds are AES-256-GCM sealed under `TWO_FACTOR_ENCRYPTION_KEY`, bound to the user id as associated data so a ciphertext copied onto another account fails; recovery codes are HMAC hashes under `OTP_PEPPER`, which production must set (startup fails without it). A correct password returns a single-use, 10-minute challenge token that only the `/api/auth/2fa` challenge and enrolment endpoints accept; no session or access token exists until the second factor passes. A code is accepted only for a TOTP step above the last accepted one, which refuses replays. Guessing is limited per challenge (5), per account (each attempt claimed atomically before it is checked; lock after 10 failures, doubling per consecutive lock up to 24 hours) and by the shared Redis limiter. SSO sign-ins are challenged like password ones until DXG answers Q8; `TWO_FACTOR_SSO_POLICY=trust_sso` is the one switch. |
| Invitations are wired to Teams, sending is capped, and Google can accept (2026-11-03, ORG-203/204 review). | An invitation may name only an active team of the inviting organization; accept re-reads the team inside the accept transaction (writing it, so a concurrent archive conflicts) and adds the member there. If the team was archived after the invitation went out, the accept still succeeds without a team (audited as `placedInTeam: false`): the person was invited into the organization, an archived team takes no new work, and refusing would leave them a dead link only an admin could replace; an admin can place them later. Because self-serve signup makes anyone an Owner whose organization name goes into the email, sending is limited per user and per organization by the shared limiter, by a daily per-organization cap on recipients (`INVITATION_DAILY_EMAIL_LIMIT`, default 500, a Mongo counter per UTC day), and by a five-minute resend cooldown per invitation checked in the write. Accounts with no usable password (Google sign-in) accept through `POST /api/v1/invitations/accept/google`, where Google's verified email stands in for the password; an `authenticate`-guarded accept was considered and dropped because a signed-in caller always has an active membership, which the accept rule refuses (`EMAIL_IN_ANOTHER_ORGANIZATION`) unless it's already in the inviting organization. |
| Requiring 2FA signs out members who haven't enrolled (ORG-304, 2026-11-02). | The PRD routes them to enrolment "on next sign-in"; revoking their refresh sessions when an Owner or Admin turns the setting on makes that sign-in happen now, so no one keeps using the app without 2FA. Until they enrol, sign-in returns only an enrolment challenge. The acting Admin must have 2FA first. An Admin reset deletes the member's enrolment and revokes all their sessions in the organization through one hook (`revokeMemberSessions`, today `authenticationSessions.revokeAll`), which ORG-307 can take over; an organization_admin cannot reset the Owner. |
| Domains are verified by a DNS TXT record, checked by a background job (ORG-305, 2026-11-02). | An Admin adds a domain and publishes `rfpilot-domain-verification=<token>` as a TXT record on it. The cron worker checks pending domains every 15 minutes for their first day, then daily, and re-checks verified ones weekly; only a definitive "no record" answer un-verifies, a DNS failure retries in an hour. `OrganizationDomain` is the source of truth and `Organization.verifiedDomains` mirrors its verified rows for the ORG-306 signup lookup; a partial unique index lets only one organization hold a domain verified. Public mail providers (and their subdomains and country variants) are never verifiable. DXG question Q7 (also accept an Admin whose email is at the domain?) is open: DNS TXT only is the default, `DOMAIN_VERIFICATION_METHODS=dns_txt,admin_email` adds the second, and such a domain stays verified only while that Admin is still an active Owner or Admin there or the TXT record exists. |
| A demotion signs the member out everywhere; other role changes don't (ORG-307, 2026-11-03). | Roles are read from the membership on every request, so any role change already applies on the member's next request without signing out, which is what ORG-307's AC asks for. For a promotion or lateral move the member's other sessions end on their next request (a lease on the pending flag, cleared only after the revocation succeeds), so the session they are using survives. A demotion by someone else revokes every session at once: the change takes rights away, and waiting for the member's next request would leave a session nobody is using (or someone else holds) alive indefinitely. A self change (the Owner after an ownership transfer) still keeps the acting session. |
| Legacy-customer placement rolls back by journaled ids (ORG-110, 2026-11-03). | A placement records the _id of every MongoDB document and the primary key of every Postgres row it moves, and rollback from an existing organization moves back exactly those, so the receiving organization's data never leaves it. RFPs given to the user later stay in the organization for an Admin to reassign. A new organization the run created is emptied and deleted whole. The Postgres move commits only after the MongoDB transaction, so a failure leaves both stores unchanged; a run that fails ORG-109's checks is rolled back immediately. |
| Accounts not yet placed in an organization can't sign in (2026-11-04, ORG-110). | Supersedes "the user's experience stays unchanged" for legacy holding tenants: every sign-in method refuses them with `ORGANIZATION_SETUP_REQUIRED` and existing sessions are ended, so each account works under an organization's rules. DXG places them (new organization as Owner, or an existing one); self-serve creation was declined because it would need the API to hold the Postgres table-owner role, so production placement runs as a one-off migrate task. |
| Publication is always human-controlled. | AI assistance must not become autonomous procurement action. |
| Investment guidance is deterministic and may refuse. | No fabricated numbers; disclose baseline provenance and unsupported categories. |
| Knowledge uses approved immutable releases. | Retrieval eligibility is tenant-scoped and excludes revoked/superseded content. |
| Client source content is untrusted data. | Prompt injection controls, strict schemas, citation allowlists, and minimized provider payloads. |
| Evaluation weightings reach vendors only once the planner confirms them (2026-07-29). | The matrix ships pre-populated and vendors are scored on it, so an untouched default set must not be published or cited as the client's criteria. `budget.evaluationMatrixConfirmed` gates both the RFP table and draft evidence; editing any weight counts as confirming. |
| Requirement registries are deterministic, versioned PostgreSQL derivatives of Mongo proposals (2026-08-12). | Task 3 needs a complete, reviewable evaluation basis before vendor evidence exists. It therefore flattens public proposal fields and human-accepted rendered narrative without a model call, records exact source locators/version/checksum, and blocks approval until a planner confirms mandatory status, criterion mapping, verification method, and matrix weights. Approved rows are database-immutable; proposal changes create visible staleness and a linked superseding version. |
| The Task 3 requirement registry is available by default without environment flags (2026-08-12). | Generation is deterministic and does not invoke a model or create provider spend. Removing three deployment flags avoids configuration drift while authentication, active membership, proposal ownership, scoped `proposal:read`/`proposal:write`, idempotency, optimistic locking, audit, and forced tenant RLS remain mandatory. Future evidence/model/evaluator capabilities retain their own release controls. |
| Schedule times are venue wall-clock, anchored to the event's time zone (2026-07-29). | Building instants in the browser's zone stored the wrong moment for any planner working outside the venue zone, and the RFP quoted vendors those times. Storage, the pickers, and draft evidence all resolve against the event zone; an unknown zone keeps machine-local behaviour. |
| Structured-output schemas use only keywords strict mode accepts (2026-07-29). | `uniqueItems` in the conversation reply schema failed every request with a 400, and because provider errors fall back silently the feature looked implemented while no planner ever received a model reply. Enforce bounds after parsing, and keep `tests/live-ai-schema-keywords.test.js` green. |
| Draft edits autosave; published proposals do not (2026-07-29). | The wizard held every step in memory with one save on the last page, so a refresh discarded hours of work. Background writes are confined to unsubmitted drafts so they can never alter what vendors already see; `Update RFP` stays explicit. |
| Expiry is a published-proposal lifecycle (2026-07-29). | `isActive` defaults to true, so an unsubmitted draft was warned about and then closed as `rejected` a week after creation. The sweep now excludes `status: "unsubmitted"`. |
| A work email on a verified domain asks to join, never auto-joins (ORG-306, 2026-11-08). | Two colleagues on one domain each created their own organization. Signup now offers "Request access" to the organization that verified the domain (verified only: a claimed domain proves nothing), approved by its Owners/Admins or automatically when they opt in. Approval sends an ordinary invitation so the accept page and its email check stay the only way in. Creating a separate organization stays possible but must be chosen. |
| Members' proven emails also match a domain; auto-approve stays DNS-only (ORG-306 follow-up, 2026-11-08). | Verified-only left a gap in production: nobody had verified a domain (verification runs only from "Check now" while the cron is off), so a colleague of an existing Owner was offered a new organization. Every account's email was proven by code or SSO when it was made, so an active member on a domain is good evidence the company already uses RFPilot. DNS-verified organizations still win; otherwise the oldest organization with an active member on the domain is offered. The match only offers "Request access" (an admin still approves), so a wrong guess costs a click on "Create a separate organization"; auto-approve, which admits without review, needs DNS proof and the API refuses it without a verified domain. Public mail providers and RFC 2606 example domains never match. |
| An RFP's lifecycle stage is derived and stored, and awarding is explicit or a comparison selection (ORG-403, 2026-11-09). | The stored `status` field couldn't answer the dashboard's questions: `reviewed` and `approved` were never set by any code path, nothing recorded an award, and the expiry sweep's `rejected` meant "expired", not "lost". `Proposal.lifecycle.stage` is now recomputed from stored facts after every write: status/draft/archive flags, the vendor-response count, the time a comparison was first opened (under review), and an award. DXG chose the award rule: a planner's "Mark as awarded" (`POST /api/proposals/:id/award`) or a final `selection` recorded in a vendor comparison. A later shortlist or no-award decision withdraws a comparison award, and a comparison never overrides a planner's award. The stage is denormalized onto the proposal so ORG-401's dashboards filter and count by an index instead of joining three collections per request. Every stage or status change appends a `ProposalStatusTransition` row (actor, reason, time). These rows are append-only and outlive a deleted proposal. Writes use compare-and-set on a revision, retried up to four times. A hook that still fails logs and leaves the primary write in place, and `npm run backfill:proposal-lifecycle` repairs drift. A guard test lists every proposal writer, so a new one has to be classified. |
| The organization vendor list is member-only data, edited by three roles and archived instead of deleted (ORG-606, 2026-11-10). | DXG decided (Q4, follow-up F6) that each organization shares one list of vendor companies and contacts, edited by Owner, Admin and Team Manager and picked from when sending an RFP. Two new coarse actions carry that rule in `authorizationPolicy.ts`: `vendor-list:write` for those three roles and `vendor-list:read` for every role that can create RFPs (so Planners too); Viewers and knowledge-only roles get neither, because the list holds third parties' contact details and only people who send RFPs need them. The list lives in Mongo (`OrganizationVendor`) with `organizationId` on every query, and a foreign id answers 404 like a missing one. Vendors are outside the trust boundary: the routes take a member session only, never a public access grant, and nothing in the vendor portal reads the model (a test enforces both). The ticket asks for CRUD and an `archived` flag; we read "delete" as archive plus restore, with no hard delete, so a mistaken removal doesn't lose contacts. Active company names are unique per organization, ignoring case, so the shared list doesn't fill with duplicates. Audit events record what changed and the contact count, never names or emails. |
| RFPilot Support reads customer RFP data only under an organization's grant (ORG-404, 2026-11-10). | DXG staff sit outside every customer organization, so there was no accountable way for them to look at an RFP. An Owner or Admin now issues a `SupportAccessGrant` for one RFP or the whole organization (7 days by default, 30 at most, revocable). The grant is to RFPilot Support as a whole, not a named agent, because customers never see the staff list; the audit event names the agent. The new admin routes take the organization in the path, check for an active grant on every request, and answer 403 without one whether or not the organization exists, and 404 for an RFP the grants don't cover, so staff can't probe ids. Only an `admins` account with a staff role qualifies; a member holding a staff membership role does not. Each read writes `support_access.used` in the customer's organization before data is returned, and fails closed if the event can't be written; refused attempts write `support_access.denied`. Customers see activity attributed to "RFPilot Support" plus a stable agent id, not a staff name, matching the helpdesk. Grants and activity live in MongoDB beside the other access records, and the reads name the granting organization explicitly rather than switching the staff member's tenant context. Helpdesk tickets stay readable without a grant; the requester's RFPs behind a ticket need one. The existing admin proposals and clients routes still read only the staff member's own organization and were left alone. |
| Plan limits are enforced by the server, per organization, on a counter that only goes up (ORG-601, 2026-11-10). | DXG priced by RFPs created with a free trial of 2 and vendor responses and RFP intelligence locked (Q2; follow-ups F1–F4 built as assumed). The plan table in `src/modules/entitlements/domain/plans.ts` is the single definition; the client only displays it. An RFP is inserted in the same MongoDB transaction as one conditional increment of `Organization.proposalsCreated`, so two creates racing for the last slot can't both pass, a failed insert uses no slot, and deleting never frees one. Locked features are refused by route middleware that reads the session organization's plan on every request, so a plan change applies at once and the answer never depends on ids in the request. Interpretations: an absent or unknown plan is the free trial; legacy holding tenants are exempt; vendor-response analysis needs both features; vendors can always submit and planners can always send, record a response for a vendor and delete one by id; retention and legal-hold routes for intelligence data are locked with the rest. `full_access` (no limit, both features) is the plan DXG staff assign until paid plans are defined; an Owner can't choose it at onboarding. Organizations that existed before this shipped keep `proposalsCreated` as stored (0), so earlier RFPs aren't counted unless DXG asks for a backfill; RFPs moved in by legacy-customer placement (ORG-110) aren't counted either. The "new vendor response" notification for a locked organization carries no vendor name, contact or total. Known limits: the durable worker doesn't re-read the plan, so intelligence jobs already queued when a plan is lowered still run (their results stay locked), which matters only once ORG-603 allows lowering a plan; and uploaded vendor document names and sizes remain listed by the document-source routes. |
| Only RFPilot staff change an organization's plan, and a downgrade applies at once while queued jobs finish (ORG-603, 2026-11-10). | Plans decide what a customer may use (DXG decision Q2), so who can set one is a trust boundary. `PUT /api/v1/admin/organization-plans/:organizationId` is the only route that can set `full_access`, and it needs both a staff membership role and an `admins` account (the same double check as support access, ORG-404), so neither a customer Owner nor a member who was handed a staff role can raise a plan. Both staff roles (`admin`, `super_admin`) may change plans: the ticket says "DXG staff", and narrowing it to super admins is a one-line change if DXG wants that. An Owner still reaches `plan` only through onboarding, which offers the self-service list (`free_trial`); onboarding now keeps a plan staff assigned instead of overwriting it. The plan and its `organization.plan_changed` audit event are written in one MongoDB transaction, in the organization whose plan changed, so the customer's audit trail shows it and a plan never changes without a record. The write is conditional on the plan that was read; a concurrent change is a 409. Staff see organization names, plans and RFP counts across organizations, and nothing about members or RFP content (that still needs a support grant). Legacy holding tenants are exempt from plans and read as not found. Lowering a plan is allowed and is not destructive: RFPs, stored vendor responses and the created count stay; the gates read the plan per request, so the features lock and creation stops at the limit immediately. The durable worker doesn't re-read the plan, so intelligence jobs already queued at a downgrade run to completion and their results stay locked until the plan is raised again. We accept that: the jobs were legitimately requested, cancelling them would need a plan check in every worker handler, and a downgrade is a rare staff action. Revisit if paid plans meter AI usage. |
| RFP templates have two ownership scopes, and a template carries content only (ORG-604, 2026-11-10). | DXG decided (Q4, follow-up F6) that organizations share RFP templates and that Planners keep their own. `ProposalTemplate.scope` is the boundary: a personal template belongs to the member who saved it and no other role can list, open, use or publish it, Owners and Admins included; an organization template belongs to the organization, is managed by Owners and Admins (`template:publish`) and is usable by every role that can create RFPs (`template:use`) while it is published. Viewers get neither action. Interpretations: publishing moves a manager's own personal template to the organization for good, and unpublishing leaves it an organization template that only Owners and Admins see, so it never falls back into one person's private list; archiving unpublishes, so a restore can't silently put a template back in the picker; another member's personal template answers 403 and another organization's 404, as RFPs do. The snapshot is an allowlist of content sections with every date, schedule time, contact person, uploaded file and co-vendor removed, and it drops the contact section and uploads entirely, because a shared template would otherwise hand one planner's contact details and private documents to every member. Saving needs view access to the source RFP (the same rule as a copy). An RFP started from a template is created by the proposals module's own create path, so it is owned by its creator, lands on their team, records its lifecycle and takes a plan slot; the template module never writes an RFP. The RFP record does not store which of the two presentation layouts it uses, so the template records the layout the client names when saving. |
